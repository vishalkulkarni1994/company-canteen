Agentic loop & tool calling

A comprehensive interview guide explaining what an agentic loop is, why it's the hardest part of AI integration, and exactly how we implemented it in our canteen app — with code walkthrough, interview Q&A, and comparison to RAG and MCP.

What is an agentic loop?

An agentic loop is a pattern where an AI model doesn't just answer a question — it takes actions, observes results, and decides what to do next in a loop until the task is complete. Instead of one request → one response, the AI becomes an agent that can interact with the real world.

Simple LLM call one-shot

User asks → LLM responds → done.

Like asking someone a question and getting an answer. The LLM can only use what it already knows.

Agentic loop multi-round

User asks → LLM thinks → calls a tool → gets data → thinks again → maybe calls another tool → finally responds.

Like hiring an assistant who can look things up, make calls, and get things done for you.

Tool calling — the mechanism

Tool calling (also called "function calling") is the mechanism that makes agentic loops possible. You tell the LLM: "Here are functions you can call and their parameters." The LLM doesn't execute the functions itself — it returns a structured request saying "I want to call function X with parameters Y." Your code then executes the function, feeds the result back to the LLM, and the cycle continues.

Key insight: The LLM never runs code itself. It only decides which tool to call and what arguments to pass. Your application code is what actually executes the tool and returns the result. This is a critical safety boundary.

Why it's the hardest part

Building an agentic loop is harder than a simple API call because you must solve several problems simultaneously:

  1. The loop itself

    You need a while/for loop that keeps calling the API until Claude says "I'm done" (returns stop_reason: "end_turn" instead of "tool_use"). Getting this right means handling both exit conditions and preventing infinite loops.

  2. Message protocol

    Claude's conversation protocol is strict. After Claude returns a tool_use block, you must send the tool result back as a user message with type: "tool_result" and the matching tool_use_id. One mismatch and the API returns a 400 error.

  3. Tool definitions with JSON Schema

    Each tool needs a name, description, and input_schema (JSON Schema). The description is crucial — it tells Claude when to use the tool. A bad description means Claude calls the wrong tool or doesn't call any.

  4. Separation of concerns

    The loop logic (call API, check stop_reason, feed results back) should be separate from business logic (what tools exist, what they do). Otherwise you end up with a monolithic class that's impossible to test or reuse.

  5. Error handling across rounds

    What if the API call fails on round 3 of 5? What if a tool throws an exception? What if Claude asks for a tool that doesn't exist? Each failure mode needs handling without corrupting the conversation state.

  6. Safety cap

    Without a maximum iteration count, a confused model could loop forever, burning API credits. You need a MaxToolRounds constant (we use 10) as a circuit breaker.

Step-by-step walkthrough

Let's trace what happens when a user types "I want to order 2 chai" in the chat:

  1. Angular → ChatController

    The Angular ChatComponent sends a POST to /api/chat with the message and JWT token. The controller extracts userId from the JWT claims and calls ChatService.SendMessage().

  2. ChatService → ClaudeApiService

    ChatService calls claudeApi.SendAsync() passing: the user's message, the agent definition (model, system prompt, tools), and a dispatchTool callback that captures the user's ID via a lambda closure: (toolName, input) => DispatchTool(toolName, input, userId).

  3. Round 1: Claude decides to check the menu

    Claude receives the user's message with two available tools. It reasons: "The user wants to order chai, I should first check if it's available." It returns:

    {
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me check today's menu for chai." },
    { "type": "tool_use", "id": "toolu_01X...", "name": "get_today_menu", "input": {} }
  ]
}
  4. ClaudeApiService executes the tool

    The loop sees stop_reason: "tool_use", finds the tool_use block, and calls the dispatchTool callback. This triggers ChatService.DispatchTool("get_today_menu", {}), which queries the SQLite database and returns JSON with today's menu items.

  5. Feed result back as a message

    The loop adds Claude's response as an assistant message, then adds the tool result as a user message with type: "tool_result" and the matching tool_use_id. This is Claude's conversation protocol — tool results must come from the user role.

  6. Round 2: Claude confirms and places the order

    Claude now has the menu data. It sees chai is available (say, menuItemId: 5, price: ₹15, 20 remaining). It returns another tool_use for place_order with {"items": [{"menuItemId": 5, "quantity": 2}]}.

  7. ClaudeApiService executes place_order

    The callback routes to PlaceOrder(), which validates stock, creates an Order entity, updates DailyStock.QuantityOrdered, saves to the database, and returns "Order #42 placed! 2x Chai. Total: ₹30".

  8. Round 3: Claude responds with final text

    Claude gets the order confirmation and returns stop_reason: "end_turn" with a friendly message: "Your order for 2 chai (₹30) has been placed! Order #42 is now being prepared." The loop exits, the text is returned through the call stack to Angular.

3 rounds, 3 API calls, 2 tool executions — all invisible to the user. They just see "I want 2 chai" → "Your order has been placed!" The agentic loop made three separate decisions autonomously.

Code deep-dive

Let's look at the actual code for each layer with annotations on why each line matters.

The agentic loop — ClaudeApiService.cs

This is the heart of the system. It's ~50 lines that handle any number of tool-calling rounds:

public async Task<string> SendAsync(
    string query,
    ClaudeAgentDefinition agentDef,
    Func<string, JsonElement, Task<string>> dispatchTool,  // callback
    List<ChatMessage>? history = null,
    CancellationToken ct = default)
{
    // Build conversation: history + new user message
    var messages = new List<object>();
    if (history != null)
        foreach (var msg in history)
            messages.Add(new { role = msg.Role, content = msg.Content });
    messages.Add(new { role = "user", content = query });

    string result = string.Empty;

    // THE LOOP — max 10 rounds to prevent runaway costs
    for (var round = 0; round < MaxToolRounds; round++)
    {
        // Call Claude via whichever client is injected (HTTP or SDK)
        var response = await client.SendAsync(agentDef, messages, ct);

        // EXIT CONDITION: Claude is done talking
        if (response.StopReason != "tool_use")
        {
            result = string.Join("\n", response.Content
                .Where(b => b.Type == "text")
                .Select(b => b.Text));
            break;  // ← loop exits here
        }

        // CONTINUE: Claude wants to use tools
        // Add Claude's response to conversation
        messages.Add(new {
            role = "assistant",
            content = response.Content.Select(b => b.Type == "text"
                ? (object)new { type = "text", text = b.Text }
                : new { type = "tool_use", id = b.Id,
                        name = b.Name, input = b.Input }
            ).ToArray()
        });

        // Execute each tool call via the callback
        var toolResults = new List<object>();
        foreach (var block in response.Content
                     .Where(b => b.Type == "tool_use"))
        {
            var toolResult = await dispatchTool(block.Name!, block.Input);
            toolResults.Add(new {
                type = "tool_result",
                tool_use_id = block.Id,
                content = toolResult
            });
        }

        // Add results as "user" message (Claude's protocol)
        messages.Add(new { role = "user",
                           content = toolResults.ToArray() });
        // Loop continues → next round
    }

    return result;
}

The callback pattern — ChatService.cs

The key design decision: ClaudeApiService doesn't know what tools exist. It receives a Func<string, JsonElement, Task<string>> callback. ChatService provides this callback with a lambda that captures userId:

// ChatService passes this to ClaudeApiService:
dispatchTool: (toolName, input) => DispatchTool(toolName, input, userId)

// The dispatch method routes by tool name:
private async Task<string> DispatchTool(
    string toolName, JsonElement input, int userId)
{
    using var scope = scopeFactory.CreateScope();  // fresh DI scope
    var db = scope.ServiceProvider
                  .GetRequiredService<CanteenDbContext>();

    return toolName switch
    {
        "get_today_menu" => await GetTodayMenu(db),
        "place_order"    => await PlaceOrder(db, input, userId),
        var unknown      => throw new NotSupportedException(
                                $"Unknown tool '{unknown}'.")
    };
}

Why IServiceScopeFactory? ClaudeApiService is a singleton (it holds no per-request state). But CanteenDbContext is scoped (one per HTTP request). When a tool callback fires during the loop, the original request scope may not match. Creating a fresh scope with scopeFactory.CreateScope() gives each tool execution its own clean database context.

Tool definitions — the JSON Schema

Claude needs to know what tools are available and what parameters they accept. This is defined as JSON Schema objects:

new {
    name = "place_order",
    description = "Place an order for the user. Each item needs a "
                + "menuItemId and quantity. Only call this after "
                + "confirming the order details with the user.",
    input_schema = new {
        type = "object",
        properties = new {
            items = new {
                type = "array",
                description = "List of items to order",
                items = new {
                    type = "object",
                    properties = new {
                        menuItemId = new { type = "integer" },
                        quantity   = new { type = "integer" }
                    },
                    required = new[] { "menuItemId", "quantity" }
                }
            }
        },
        required = new[] { "items" }
    }
}

The description is critical — it's the natural-language instruction that tells Claude when and how to use the tool. Notice the instruction "Only call this after confirming the order details" — this prevents Claude from placing orders without user confirmation.

Interview Q&A

Common interview questions about agentic loops and tool calling, answered with examples from our canteen app.

What is an agentic loop and how does it differ from a simple API call?

A simple API call is one request, one response — like asking "translate this to French." An agentic loop is a multi-round conversation where the AI can take actions between rounds. The AI decides what to do, executes tools, observes results, and keeps going until the task is complete.

In our canteen app, when a user says "order 2 chai," Claude autonomously decides to: (1) check today's menu, (2) verify chai is available, (3) place the order. That's 3 API rounds with 2 tool calls, all invisible to the user.

What is tool calling / function calling?

Tool calling is the mechanism where you define functions (tools) with their parameters as JSON Schema, send them to the LLM alongside the user's message, and the LLM can request to call these functions. The LLM doesn't execute anything — it returns a structured object saying "call function X with arguments Y." Your code executes the function and feeds the result back.

In our app, we define two tools: get_today_menu (no params) and place_order (takes an array of items). Claude decides which to call based on the conversation context.

How do you prevent infinite loops when the AI keeps calling tools?

We use a MaxToolRounds = 10 constant as a circuit breaker. The loop runs inside a for loop capped at 10 iterations. In practice, a typical canteen interaction takes 2-3 rounds. If something goes wrong and Claude keeps requesting tools, the loop exits after 10 rounds and returns whatever text Claude has produced so far.

for (var round = 0; round < MaxToolRounds; round++)
{
    var response = await client.SendAsync(agentDef, messages, ct);
    if (response.StopReason != "tool_use")
        break;  // Claude is done
    // ... execute tools and continue
}
How do you separate business logic from the AI orchestration?

We follow a callback pattern inspired by the V3 TradeCapture pipeline separation. ClaudeApiService owns the loop but knows nothing about canteen logic. ChatService owns the tools and business logic but knows nothing about the API protocol. They communicate through a Func<string, JsonElement, Task<string>> delegate.

This means ClaudeApiService is reusable — you could build a completely different AI feature (analytics, recommendations) by just providing different tool definitions and a different dispatch callback. The loop code stays identical.

What is the stop_reason and why does it matter?

Claude's API returns a stop_reason field that tells you why the response ended:

  • "end_turn" — Claude is done. Extract the text and return it to the user.
  • "tool_use" — Claude wants to call one or more tools. Execute them and feed the results back.
  • "max_tokens" — The response was cut off because it hit the token limit.

The stop_reason is the control signal that drives the loop. Our code checks if (response.StopReason != "tool_use") break; — any stop reason other than tool_use exits the loop.

Why do tool results go in a "user" role message?

This is Claude's conversation protocol. The message sequence must alternate between user and assistant roles. When Claude returns a tool_use block, that's an assistant message. The tool results must come back as a user message so the alternation continues.

Each tool result must include the tool_use_id from the original request so Claude can match results to the tools it called. Without this ID, the API returns a 400 error.

// Add Claude's tool request as assistant message
messages.Add(new { role = "assistant", content = ... });

// Add tool results as user message
messages.Add(new { role = "user", content = new[] {
    new { type = "tool_result",
          tool_use_id = block.Id,    // must match!
          content = toolResult }
}});
What is the strategy pattern in your Claude integration?

We use the strategy pattern for the transport layer. The IClaudeMessageClient interface defines the contract: SendAsync(agentDef, messages, ct) returns ClaudeResponse. Two implementations exist:

  • HttpClaudeClient — Raw HTTP with manual JSON serialization (default)
  • SdkClaudeClient — Anthropic SDK package (opt-in via config)

A boolean flag in appsettings.json ("UseSdk": false) controls which implementation gets registered in DI. The agentic loop in ClaudeApiService works identically with either one.

How do you handle DI scoping when a singleton service needs scoped dependencies?

ClaudeApiService is registered as a singleton (it holds no per-request state). But each tool call needs a fresh CanteenDbContext, which is scoped. We solve this with IServiceScopeFactory:

private async Task<string> DispatchTool(...)
{
    using var scope = scopeFactory.CreateScope();
    var db = scope.ServiceProvider
                  .GetRequiredService<CanteenDbContext>();
    // ... use db, scope disposes when done
}

Each tool execution creates its own DI scope, gets a fresh DbContext, uses it, and disposes it when the using block ends. This is the standard pattern for singletons that need scoped services.

What happens if Claude calls a tool that doesn't exist?

Our DispatchTool method uses a C# switch expression with a discard pattern as the fallback:

return toolName switch
{
    "get_today_menu" => await GetTodayMenu(db),
    "place_order"    => await PlaceOrder(db, input, userId),
    var unknown      => throw new NotSupportedException(
                            $"Unknown tool '{unknown}'.")
};

In practice, Claude almost never calls a non-existent tool because the tool definitions constrain what it knows about. But the guard is there for safety. The exception is caught by the try/catch in ChatService.SendMessage(), which returns a friendly error to the user.

How does the lambda closure capture the user ID?

When ChatService calls the agentic loop, it passes a lambda that closes over userId:

return await claudeApi.SendAsync(
    userMessage,
    AgentDef,
    dispatchTool: (toolName, input) =>
        DispatchTool(toolName, input, userId),  // userId captured here
    history,
    CancellationToken.None);

ClaudeApiService never sees or knows about userId. It just calls the delegate. The lambda captures userId from the enclosing scope, so when place_order runs three rounds later, it still knows which user to create the order for.

This is a powerful pattern — the generic loop becomes user-aware without any user-specific code.

Can Claude call multiple tools in a single round?

Yes. Claude can return multiple tool_use blocks in a single response. Our loop handles this with a foreach that iterates over all tool_use blocks:

foreach (var block in response.Content
             .Where(b => b.Type == "tool_use"))
{
    var toolResult = await dispatchTool(block.Name!, block.Input);
    toolResults.Add(new { type = "tool_result",
                          tool_use_id = block.Id,
                          content = toolResult });
}

All tool results are collected and sent back as a single user message. This is called parallel tool use — Claude might decide to check the menu AND look up user preferences in one round.

How would you add a new tool to the system?

Three steps, all in ChatService.cs only:

  1. Define the tool — add a JSON Schema object to BuildToolDefinitions()
  2. Add the route — add a case to the switch in DispatchTool()
  3. Implement the logic — write the method that executes the tool

No changes needed in ClaudeApiService, HttpClaudeClient, the controller, or the frontend. This is the power of the separation — adding new capabilities is purely a business logic task.

Tool calling vs RAG vs MCP

Interviewers often ask you to compare these. Here's a clear breakdown:

AspectTool callingRAGMCP
What it does LLM calls functions to take actions or fetch structured data Search documents/text to add context before asking the LLM Standardized protocol for connecting LLMs to external tools/data
Data type Structured (databases, APIs, functions) Unstructured (documents, PDFs, knowledge bases) Any (it's a transport protocol)
Who decides? The LLM decides which tool to call and with what params Your code decides what to search; LLM uses the retrieved context The LLM decides (MCP tools are tool calls over a protocol)
Loop? Yes — multi-round agentic loop Usually single-shot: retrieve → augment → generate Yes — the MCP client runs an agentic loop
Example User says "order chai" → Claude calls place_order User asks "is paneer gluten-free?" → search allergen docs → answer Claude Desktop connects to your app via MCP protocol
Our canteen app Used ClaudeApiService agentic loop Not yet Could add for nutrition/allergen docs Not yet Could expose canteen as MCP server

Key interview answer: MCP uses tool calling under the hood. The difference is where the loop runs and how tools are connected. With direct tool calling, you own the loop. With MCP, the MCP client (like Claude Desktop) owns the loop, and your app just exposes tools as an MCP server.

Production gotchas

Things interviewers like to hear you've thought about:

Cost control

Each loop round is a separate API call. A 3-round interaction sends the full conversation each time, so input tokens compound. We use claude-haiku-5-5 (cheapest at $0.10/$0.50 per MTok) and track token usage across rounds for monitoring.

Idempotency

If the API call fails after place_order runs but before Claude gets the result, retrying the loop could place a duplicate order. In production, tool calls that mutate state should be idempotent (e.g., use an idempotency key).

Tool descriptions matter

Claude decides which tool to call based on the description field, not the function name. A vague description like "do stuff with orders" leads to incorrect tool usage. We write specific descriptions: "Only call this after confirming the order details with the user."

Security boundary

Claude can only call tools you define. It can't access the filesystem, network, or database directly. Each tool is a controlled API — place_order validates stock, checks the user, and enforces business rules. The LLM is sandboxed by the tool definitions.

Context window growth

Each round appends to the messages array. By round 5, the input includes all previous tool calls and results. With large tool responses, this can hit Claude's context limit. Solutions: summarize old tool results, or cap tool response size.

Streaming

Our current implementation waits for the full response. In production, streaming (SSE) gives users instant feedback. The challenge: with streaming, you need to detect tool_use blocks from the stream, which adds complexity to the loop.
