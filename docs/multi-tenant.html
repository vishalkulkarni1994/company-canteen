Multi-tenant architecture

Every piece of data — menu items, orders, stock, analytics — is scoped to a Company. Users belong to exactly one company, and the system enforces data isolation from the JWT claim through every query. A SuperAdmin role provides cross-company visibility.

Overview

The canteen system serves multiple independent companies from a single database. Each company has its own menu, stock, orders, and users. The tenant boundary is enforced at two levels:

  1. JWT claim: Every authenticated request carries a CompanyId claim, extracted via ClaimsPrincipalExtensions
  2. Query filter: Every database query filters by CompanyId, preventing cross-company data leaks

Single-tenant before

  • One shared menu for everyone
  • Two roles: Admin and Employee
  • All users see all orders
  • One analytics pool

Multi-tenant after

  • Each company has its own menu
  • Three roles: User, CompanyAdmin, SuperAdmin
  • Data isolated by CompanyId on every entity
  • Analytics scoped per company; SuperAdmin sees all

Isolation strategy: shared database, filtered queries. All companies share one SQLite database. Isolation is enforced by filtering every query with WHERE CompanyId = @companyId. This is simpler than database-per-tenant and sufficient for our scale. The tradeoff: a bug in a query filter could leak data between companies. Every controller method extracts CompanyId from the JWT and passes it to EF Core queries.

EF Core configuration

CanteenDbContextDbContext

File server/Data/CanteenDbContext.cs

Key configuration details for the Company entity and its relationships:

// Unique company name constraint
modelBuilder.Entity<Company>()
    .HasIndex(c => c.Name).IsUnique();

// User → Company: optional (SuperAdmin has no company)
modelBuilder.Entity<User>()
    .HasOne(u => u.Company)
    .WithMany(c => c.Users)
    .HasForeignKey(u => u.CompanyId)
    .OnDelete(DeleteBehavior.Restrict);

// MenuItem → Company: required
modelBuilder.Entity<MenuItem>()
    .HasOne(m => m.Company)
    .WithMany(c => c.MenuItems)
    .HasForeignKey(m => m.CompanyId)
    .OnDelete(DeleteBehavior.Restrict);

// Order → Company: required
modelBuilder.Entity<Order>()
    .HasOne(o => o.Company)
    .WithMany(c => c.Orders)
    .HasForeignKey(o => o.CompanyId)
    .OnDelete(DeleteBehavior.Restrict);

All foreign keys use DeleteBehavior.Restrict to prevent accidental cascade deletion of an entire company's data.

Role hierarchy

Three roles form a strict hierarchy. Each role inherits the permissions of the roles below it.

RoleCompanyIdCapabilities
User Required (non-null) Browse own company's menu, place orders, use AI chat, view own orders
CompanyAdmin Required (non-null) Everything a User can do, plus: manage menu items, set daily stock, view all company orders, access analytics
SuperAdmin null Everything a CompanyAdmin can do across all companies, plus: create companies, manage user roles, cross-company analytics

// Any authenticated user
function ProtectedRoute({ children }) {

// CompanyAdmin OR SuperAdmin
function AdminRoute({ children }) {
  const { user } = useAuth();
  if (user.role !== "CompanyAdmin" && user.role !== "SuperAdmin")
    return <Navigate to="/" />;
  return children;
}

// SuperAdmin only
function SuperAdminRoute({ children }) {
  const { user } = useAuth();
  if (user.role !== "SuperAdmin") return <Navigate to="/" />;
  return children;

JWT & claims

The JWT token carries the tenant context. When a user logs in, AuthService adds CompanyId as a custom claim (only when the user has a company).

AuthService.GenerateTokenJWT

File server/Services/AuthService.cs

var claims = new List<Claim>
{
    new(ClaimTypes.NameIdentifier, user.Id.ToString()),
    new(ClaimTypes.Email, user.Email),
    new(ClaimTypes.Name, user.Name),
    new(ClaimTypes.Role, user.Role),
};

// Only add CompanyId for non-SuperAdmin users
if (user.CompanyId.HasValue)
    claims.Add(new Claim("CompanyId", user.CompanyId.Value.ToString()));

Claim extraction helpers

ClaimsPrincipalExtensionsextension

File server/Extensions/ClaimsPrincipalExtensions.cs

Every controller uses these extensions to extract the tenant context from the JWT:

public static class ClaimsPrincipalExtensions
{
    public static int GetUserId(this ClaimsPrincipal user)
        => int.Parse(user.FindFirstValue(ClaimTypes.NameIdentifier)!);

    public static int? GetCompanyId(this ClaimsPrincipal user)
    {
        var val = user.FindFirstValue("CompanyId");
        return val is null ? null : int.Parse(val);
    }

    public static string GetRole(this ClaimsPrincipal user)
        => user.FindFirstValue(ClaimTypes.Role)!;

    public static bool IsSuperAdmin(this ClaimsPrincipal user)
        => user.GetRole() == "SuperAdmin";

    public static bool IsCompanyAdmin(this ClaimsPrincipal user)
        => user.GetRole() is "CompanyAdmin" or "SuperAdmin";
}

Note: IsCompanyAdmin() returns true for both CompanyAdmin and SuperAdmin. This follows the "higher role inherits lower role's permissions" pattern.

CompanyId is nullable. GetCompanyId() returns int?. SuperAdmin users have null because they exist outside any company. Every controller checks for this: regular endpoints require a non-null CompanyId (return 400 if missing), while SuperAdmin endpoints bypass the check entirely.

Controller isolation

Every API controller follows the same pattern: extract CompanyId from the JWT, filter all queries by it, and validate ownership before mutations. SuperAdmin bypasses the company filter.

The pattern

  1. Extract CompanyId from JWT

    var companyId = User.GetCompanyId();

  2. Guard: require CompanyId for regular users

    if (companyId is null) return BadRequest("No company context");

  3. Filter queries by CompanyId

    db.MenuItems.Where(m => m.CompanyId == companyId)

  4. Validate ownership on mutations

    if (item.CompanyId != companyId) return Forbid();

MenuController

MenuControllercompany-scoped

File server/Controllers/MenuController.cs

// GET: Filter by company (SuperAdmin sees all)
[HttpGet]
public async Task<IActionResult> GetAll()
{
    var companyId = User.GetCompanyId();
    var query = db.MenuItems.Where(m => m.IsActive);

    if (companyId.HasValue)
        query = query.Where(m => m.CompanyId == companyId);
    // SuperAdmin: no filter → sees all companies

    return Ok(await query.ToListAsync());
}

// POST: Assign to user's company
[HttpPost]
public async Task<IActionResult> Create(CreateMenuItemRequest req)
{
    var companyId = User.GetCompanyId();
    if (companyId is null) return BadRequest("No company context");

    var item = new MenuItem {
        Name = req.Name,
        CompanyId = companyId.Value  // ← tenant assignment
    };
    // ...
}

// PUT/DELETE: Validate ownership
[HttpPut("{id}")]
public async Task<IActionResult> Update(int id, ...)
{
    var item = await db.MenuItems.FindAsync(id);
    if (item?.CompanyId != User.GetCompanyId()) return Forbid();
    // ...
}

OrderControllercompany-scoped

// POST: Validate stock belongs to user's company
[HttpPost]
public async Task<IActionResult> PlaceOrder(PlaceOrderRequest req)
{
    var companyId = User.GetCompanyId();
    if (companyId is null) return BadRequest("No company context");

    var stocks = await db.DailyStocks
        .Include(s => s.MenuItem)
        .Where(s => s.Date == today
            && s.MenuItem.CompanyId == companyId  // ← can't order from another company
            && req.Items.Select(i => i.MenuItemId).Contains(s.MenuItemId))
        .ToListAsync();

    var order = new Order {
        UserId = userId,
        CompanyId = companyId.Value,  // ← stamp the order
        // ...
    };
}

// GET active orders: scoped to company
[Authorize(Roles = "CompanyAdmin,SuperAdmin")]
[HttpGet("active")]
public async Task<IActionResult> ActiveOrders()
{
    var companyId = User.GetCompanyId();
    var query = db.Orders.Where(o => o.Status != "Delivered");

    if (companyId.HasValue)
        query = query.Where(o => o.CompanyId == companyId);

    return Ok(await query.ToListAsync());
}

CompanyController (SuperAdmin only)

CompanyControllerSuperAdmin

File server/Controllers/CompanyController.cs

The entire controller is restricted to SuperAdmin with [Authorize(Roles = "SuperAdmin")] at the class level.

[Authorize(Roles = "SuperAdmin")]
public class CompanyController(CanteenDbContext db) : ControllerBase
{
    // List all companies with aggregate stats
    [HttpGet]
    public async Task<IActionResult> GetAll()
    {
        return Ok(await db.Companies.Select(c => new {
            c.Id, c.Name, c.CreatedAt,
            UserCount = c.Users.Count(),
            MenuItemCount = c.MenuItems.Count(m => m.IsActive),
            TodayOrders = c.Orders.Count(o => o.CreatedAt.Date == DateTime.UtcNow.Date)
        }).ToListAsync());
    }

    // Create company (unique name enforced)
    [HttpPost]
    public async Task<IActionResult> Create(CreateCompanyRequest req) { ... }

    // View users of a specific company
    [HttpGet("{id}/users")]
    public async Task<IActionResult> GetCompanyUsers(int id) { ... }

    // Promote/demote users (User ↔ CompanyAdmin only)
    [HttpPut("users/{userId}/role")]
    public async Task<IActionResult> UpdateUserRole(int userId, UpdateRoleRequest req)
    {
        if (req.Role is not ("User" or "CompanyAdmin"))
            return BadRequest("Role must be User or CompanyAdmin");
        // Can't create SuperAdmins through the API
    }
}

Security boundary. The UpdateUserRole endpoint only allows setting "User" or "CompanyAdmin". There is no API path to create a SuperAdmin — this must be done directly in the database. This is a deliberate security choice to prevent privilege escalation through the API.

AI & analytics scoping

Both the AI chat tools and the Text-to-SQL analytics are company-scoped. The tenant boundary extends into the AI layer.

Chat tool dispatch

ChatService.DispatchToolscoped tools

File server/Services/ChatService.cs

The tool dispatch closure captures companyId and passes it to every tool function. Claude can only query or modify data within the user's company.

// SendMessageStream passes a closure that captures companyId
await foreach (var evt in claudeApi.SendStreamAsync(
    message, agentDef,
    (toolName, input) => DispatchTool(toolName, input, userId, companyId),
    history, ct))
{
    yield return evt;
}

// Inside DispatchTool:
private async Task<string> DispatchTool(
    string toolName, JsonElement input, int userId, int companyId)
{
    // Every tool receives companyId and filters by it
    return toolName switch {
        "get_today_menu" => await GetTodayMenu(scope, companyId),
        "place_order" => await PlaceOrder(scope, input, userId, companyId),
        // ...
    };
}

// GetTodayMenu filters by company:
var stocks = await db.DailyStocks
    .Where(s => s.Date == today && s.MenuItem.CompanyId == companyId)
    .ToListAsync();

Text-to-SQL analytics scoping

AnalyticsService.BuildAgentDefprompt injection

File server/Services/AnalyticsService.cs

The analytics system prompt is dynamically built based on the user's role. For regular users, Claude is instructed to always filter by their CompanyId. For SuperAdmin, Claude has access to all companies.

private ClaudeAgentDefinition BuildAgentDef(int? companyId)
{
    var scope = companyId.HasValue
        ? $"ALL queries MUST filter by CompanyId={companyId}. " +
          "Never return data from other companies."
        : "You have access to all companies. " +
          "Include CompanyId grouping when relevant.";

    var systemPrompt = $"""
        You are an analytics assistant for a canteen system.
        Database schema: {schema}

        DATA ACCESS RULES:
        {scope}
        """;

    return new ClaudeAgentDefinition { System = systemPrompt, ... };
}

Defence in depth. The Text-to-SQL analytics uses Claude to generate SQL. The company filter is injected into the system prompt, not enforced at the database level. For a production system, you would also want a query validator that rejects SQL without the required WHERE CompanyId = clause. The current approach relies on Claude following the system prompt instruction.
