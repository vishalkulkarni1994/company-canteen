Placing & tracking orders

From browsing today's menu to getting a toast when your food is ready: cart management, order placement with atomic stock decrement, a kitchen kanban for admins, and polling-based notifications. Every entity, every endpoint, every component.

Updated in Phase 09 — Multi-Tenant. Orders now carry a CompanyId. Stock validation checks that menu items belong to the user's company, and the kitchen kanban is scoped per company. See the multi-tenant architecture doc for details.

Overview

The ordering system sits on top of the menu and stock layers built in phase 2. An employee browses today's available items, adds them to an in-memory cart, and places an order. The server atomically decrements stock, calculates totals, and records the order. Admin users manage the kitchen via a kanban board, advancing orders through a strict status state machine. Employees see their order history and receive real-time toast notifications when an order becomes ready for pickup.

Cart client-side

A Map<number, CartItem> held in React state. No server-side cart — items are collected locally and sent in one POST when the user clicks Place Order.

Order server-side

An Order entity with child OrderItem rows. Tracks status, total amount, and timestamps. Stock is decremented on placement and restored on cancellation.

Notifications polling

A useOrderNotifications hook polls /api/order/my/active every 10 seconds. When an order transitions to Ready, a toast appears with auto-dismiss.

Order status machine

Every order follows a strict state machine. Transitions are enforced server-side in OrderController using an AllowedTransitions dictionary. Any attempt to skip a state or go backwards returns 400 Bad Request.

FromAllowed nextWhoEffect
PlacedPreparingAdminKitchen starts making the order
PlacedCancelledEmployee (owner)Stock restored to DailyStock
PreparingReadyAdminTriggers notification toast for employee
ReadyCollectedAdminOrder leaves active set; removed from kanban

Cancellation is only allowed from the Placed state. Once the kitchen starts preparing, the food is committed. The employee must own the order to cancel it.

The Order entity holds the header: who placed it, its current status, total amount, and timestamps. OrderItem is the line item: which dish, how many, and the unit price at the time of ordering (price is captured, not referenced, so menu price changes don't alter past orders).

Place order: atomic stock decrement

POST /api/orderphase 2

The critical business logic: for each line item, the server loads today's DailyStock row, checks that enough servings remain (QuantityAvailable - QuantityOrdered ≥ requested), increments QuantityOrdered, and captures the current menu price. Everything happens inside a single SaveChangesAsync call — either the whole order succeeds or nothing changes.

[HttpPost]
public async Task<IActionResult> PlaceOrder([FromBody] PlaceOrderRequest req)
{
    var userId = int.Parse(User.FindFirst(ClaimTypes.NameIdentifier)!.Value);
    var today = DateOnly.FromDateTime(DateTime.UtcNow);
    var order = new Order { Status = "Placed", TotalAmount = 0, UserId = userId };

    foreach (var line in req.Items)
    {
        var stock = await db.DailyStocks
            .Include(s => s.MenuItem)
            .FirstOrDefaultAsync(s => s.MenuItemId == line.MenuItemId
                                     && s.Date == today
                                     && s.MenuItem.IsActive);

        if (stock is null)
            return BadRequest(new { message = $"Item {line.MenuItemId} is not available today" });

        var remaining = stock.QuantityAvailable - stock.QuantityOrdered;
        if (line.Quantity > remaining)
            return BadRequest(new { message = $"Only {remaining} servings left for {stock.MenuItem.Name}" });

        stock.QuantityOrdered += line.Quantity;

        order.Items.Add(new OrderItem
        {
            MenuItemId = line.MenuItemId,
            Quantity = line.Quantity,
            UnitPrice = stock.MenuItem.Price
        });
        order.TotalAmount += line.Quantity * stock.MenuItem.Price;
    }

    db.Orders.Add(order);
    await db.SaveChangesAsync();
    return Created($"/api/order/{order.Id}", ToResponse(order));
}

Cancel order: stock restoration

DELETE /api/order/{id}phase 2

Only allowed from Placed status. The server iterates through each order item and decrements QuantityOrdered on the corresponding DailyStock row, restoring availability for other employees.

[HttpDelete("{id}")]
public async Task<IActionResult> CancelOrder(int id)
{
    var order = await db.Orders.Include(o => o.Items)
        .FirstOrDefaultAsync(o => o.Id == id);

    if (order is null) return NotFound();
    if (order.UserId != userId) return Forbid();
    if (order.Status != "Placed")
        return BadRequest(new { message = "Only placed orders can be cancelled" });

    order.Status = "Cancelled";
    order.UpdatedAt = DateTime.UtcNow;

    var today = DateOnly.FromDateTime(DateTime.UtcNow);
    foreach (var item in order.Items)
    {
        var stock = await db.DailyStocks
            .FirstOrDefaultAsync(s => s.MenuItemId == item.MenuItemId && s.Date == today);
        if (stock is not null)
            stock.QuantityOrdered -= item.Quantity;
    }

    await db.SaveChangesAsync();
    return NoContent();
}

Status transitions

PUT /api/order/{id}/statusphase 2

Admin-only endpoint. The AllowedTransitions dictionary enforces the state machine at the controller level — no invalid transitions can sneak through.

private static readonly Dictionary<string, string[]> AllowedTransitions = new()
{
    ["Placed"]    = ["Preparing", "Cancelled"],
    ["Preparing"] = ["Ready"],
    ["Ready"]     = ["Collected"],
};

[HttpPut("{id}/status")]
[Authorize(Roles = "Admin")]
public async Task<IActionResult> UpdateStatus(int id, [FromBody] UpdateStatusRequest req)
{
    var order = await db.Orders.Include(o => o.Items).ThenInclude(oi => oi.MenuItem)
        .FirstOrDefaultAsync(o => o.Id == id);

    if (!AllowedTransitions.TryGetValue(order.Status, out var allowed)
        || !allowed.Contains(req.Status))
        return BadRequest(new { message = $"Cannot transition from {order.Status} to {req.Status}" });

    order.Status = req.Status;
    order.UpdatedAt = DateTime.UtcNow;
    await db.SaveChangesAsync();
    return Ok(ToResponse(order));
}

Phase 3: Cart + checkout UI

Cart state: Map<number, CartItem>

The cart lives as React state in TodayMenuPage.tsx. Using a Map keyed by menuItemId gives O(1) lookups when checking whether an item is already in the cart and enforcing stock limits.

CartItem interfacephase 3

File client/src/api/orders.ts

export interface CartItem {
  menuItemId: number;
  name: string;
  price: number;
  quantity: number;
  remaining: number;  // from today's stock, caps the + button
}

How adding works

  1. User clicks "Add" on a menu card

    addToCart(item) creates a new Map (immutable update). If the item already exists, quantity increments up to item.remaining. Otherwise, a fresh entry is inserted with quantity 1.

  2. Cart panel opens

    Shows each item with − / + buttons. The + button is disabled when quantity ≥ remaining. Clicking − below 1 removes the item entirely.

  3. User clicks "Place Order"

    handlePlaceOrder() maps cart entries to { menuItemId, quantity } and calls placeOrder(items). On success, the cart clears, a success banner shows the order ID and total, and the menu grid refreshes stock counts.

  4. Stock refreshes

    After a successful order, getTodayStock() is called again to update the remaining counts shown on each menu card. Items that just sold out become greyed out with a "Sold Out" badge.

placeOrder()phase 3

File client/src/api/orders.ts

export async function placeOrder(
  items: { menuItemId: number; quantity: number }[]
): Promise<OrderResponse> {
  const res = await fetch(`${API}/order`, {
    method: "POST",
    headers: authHeaders(),
    body: JSON.stringify({ items }),
  });
  if (!res.ok) {
    const err = await res.json().catch(() => null);
    throw new Error(err?.message || "Failed to place order");
  }
  return res.json();
}

Phase 5: Kitchen kanban

5
KitchenPage for admins
Three-column kanban board with auto-refresh, showing all active orders grouped by status.

The kitchen view at /admin/orders is admin-only. It fetches GET /api/order/active (which returns all orders where status is Placed, Preparing, or Ready, including the customer name), groups them into three columns, and auto-refreshes every 15 seconds.

Kanban columns

Placed

New orders waiting to be started. Each card shows order ID, customer name, items list, and total. Button: Start → moves to Preparing.

Preparing

Orders currently being made. Button: Mark Ready → moves to Ready (and triggers notification for the employee).

Ready

Waiting for pickup. Button: Collected → removes from the board entirely.

Phase 6: Order-ready notifications

6
Toast notifications via polling
A global hook that polls for status changes and shows a green toast when an order moves to Ready.

The notification system uses a polling-first approach (SignalR planned for later). Three components work together:

Architecture

  1. New endpoint: GET /api/order/my/active

    Returns the user's orders where status is Placed, Preparing, or Ready. Lighter than /my because it excludes completed and cancelled orders.

  2. Polling hook: useOrderNotifications

    Runs inside AppShell (above the router) so it polls regardless of which page the user is on. Every 10 seconds it fetches active orders and compares each order's current status with the previous poll's snapshot. When an order transitions to "Ready", a toast is enqueued.

  3. Toast component: ToastContainer

    Renders a stack of green banners in the top-right corner. Each toast slides in, auto-dismisses after 8 seconds, and can be manually closed.

The polling hook

useOrderNotificationsphase 6

File client/src/hooks/useOrderNotifications.ts

The hook stores a Map<orderId, status> in a useRef to survive across renders without triggering them. On each poll, it builds a fresh map and compares old vs. new status per order.

const POLL_INTERVAL = 10_000;

export default function useOrderNotifications(loggedIn: boolean) {
  const [toasts, setToasts] = useState<ToastMessage[]>([]);
  const prevStatuses = useRef<Map<number, string>>(new Map());

  useEffect(() => {
    if (!loggedIn) { prevStatuses.current.clear(); return; }

    async function check() {
      const orders = await getMyActiveOrders();
      const prev = prevStatuses.current;
      const next = new Map<number, string>();

      for (const order of orders) {
        const oldStatus = prev.get(order.id);
        next.set(order.id, order.status);

        if (oldStatus && oldStatus !== order.status && order.status === "Ready") {
          const itemNames = order.items.map(i => i.name).join(", ");
          setToasts(t => [...t, {
            id: `ready-${order.id}-${Date.now()}`,
            text: `Order #${order.id} is ready for pickup! (${itemNames})`,
          }]);
        }
      }
      prevStatuses.current = next;
    }

    check();
    const polling = setInterval(check, POLL_INTERVAL);
    return () => clearInterval(polling);
  }, [loggedIn]);

  return { toasts, dismiss };
}

AppShell integration

AppShellphase 6

File client/src/App.tsx

The AppShell wrapper sits inside AuthProvider but outside BrowserRouter. This lets it access the auth context to know whether to poll, while rendering the toast overlay above all routes.

function AppShell() {
  const { user } = useAuth();
  const { toasts, dismiss } = useOrderNotifications(!!user);

  return (
    <>
      <ToastContainer messages={toasts} onDismiss={dismiss} />
      <BrowserRouter>
        <Routes>{/* ... all routes ... */}</Routes>
      </BrowserRouter>
    </>
  );
}

Why polling, not WebSockets? Polling is simpler to deploy (no sticky sessions, no SignalR hub). At canteen scale (< 100 concurrent users), a 10-second GET request per user is negligible server load. SignalR can be added later for instant push when the user base grows.
