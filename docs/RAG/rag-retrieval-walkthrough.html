RAG Retrieval — Step-by-Step Walkthrough

How a user’s knowledge question travels through the system: from chat input, to Claude’s tool decision, through vector search, and back as a grounded answer. 4 files, 5 methods, one round trip.

Retrieval Flow Diagram

Every knowledge question follows this exact path. The key insight: retrieval is tool-driven, not always-on. Claude decides when to search.

The Retrieval Round Trip
1 User: “Does chicken biryani contain nuts?”
↓ POST /api/chat/stream → ChatController extracts userId, companyId from JWT
↓ ChatService.SendMessageStream()
↓
2 Claude sees 3 tools: get_today_menu, place_order, search_knowledge
↓ Reads system prompt: “use search_knowledge for ingredients, allergens, policies”
↓ Decides: this is a knowledge question, not an order
↓ Returns tool_use: search_knowledge({ "query": "chicken biryani nuts allergens" })

A specific description (“recipes, ingredients, allergens, nutrition, canteen policies”) = precise routing. This is cheaper and more flexible than writing regex or keyword matching yourself.

Claude Picks search_knowledge

ClaudeApiService.cs — The agentic loop receives a tool_use response from Claude.

When the user asks “Does chicken biryani contain nuts?”, Claude sees three tools and must choose. It reasons:

  • get_today_menu — retrieves today’s menu items and stock. Not relevant.
  • place_order — places an order. Not relevant.
  • search_knowledge — “allergens, ingredients, nutrition” matches perfectly.

Claude returns:

{
  "type": "tool_use",
  "id": "toolu_01abc...",
  "name": "search_knowledge",
  "input": {
    "query": "chicken biryani nuts allergens ingredients"
  }
}
Claude reformulates the query. The user said “Does chicken biryani contain nuts?” but Claude sends “chicken biryani nuts allergens ingredients” to the search tool. It strips the question format and adds related terms (allergens, ingredients) to cast a wider net for the embedding search. This is free query expansion — we didn’t code it, Claude does it naturally.

DispatchTool — String Match to Method Call

ChatService.cs — DispatchTool(), lines 67–80

The agentic loop in ClaudeApiService extracts the tool name ("search_knowledge") and input JSON, then calls the dispatchTool delegate. In ChatService, this is a switch expression:

private async Task<string> DispatchTool(
    string toolName, JsonElement input, int userId, int companyId)
{
    using var scope = scopeFactory.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<CanteenDbContext>();

    return toolName switch
    {
        "get_today_menu"   => await GetTodayMenu(db, companyId),
        "place_order"      => await PlaceOrder(db, input, userId, companyId),
        "search_knowledge" => await ragService.SearchAsync(
                                  input.GetProperty("query").GetString()!, companyId),
        var unknown        => throw new NotSupportedException($"Unknown tool '{unknown}'.")
    };
}
LineWhat happens
input.GetProperty("query")Extracts the query property from Claude’s JSON input
.GetString()!Converts to string (the ! is null-forgiving — we know it’s present because the schema says required)
ragService.SearchAsync(..., companyId)Passes the query and the company ID from the JWT — this is how tenant isolation starts
No magic. The mapping is a string match in a switch expression. Claude returns "search_knowledge" as a string, the switch matches it, and calls RagService.SearchAsync(). Same pattern as a controller routing a URL to a method — the tool name is effectively a “route.”

Query Embedding — Text to Vector

EmbeddingService.cs — EmbedAsync(), line 14

Before we can search, the query string must become a vector in the same embedding space as the stored documents. If we used a different model or even a different deployment, the similarity scores would be meaningless.

// RagService.cs line 10 — first thing SearchAsync does
var queryVec = await embedding.EmbedAsync(query, ct);

EmbedAsync delegates to EmbedBatchAsync with a single-item list:

public async Task<float[]> EmbedAsync(string text, CancellationToken ct = default)
{
    var results = await EmbedBatchAsync([text], ct);
    return results[0];
}

Tenant-Filtered Load from SQLite

RagService.cs — SearchAsync(), lines 15–18

Load only this company’s chunks from the database. This is the first line of tenant isolation — Company A’s documents are never even loaded into memory when Company B’s user searches.

// RagService.cs — load company chunks
var chunks = await db.DocumentChunks
    .Where(c => c.CompanyId == companyId)       // TENANT ISOLATION
    .Select(c => new { c.Title, c.Content, c.Source, c.Embedding })
    .ToListAsync(ct);
DetailWhy
.Where(CompanyId == companyId)Pre-filter: only this company’s chunks leave the database. Zero data leakage.
.Select(new { ... })Project only the columns we need — avoids loading the full Company navigation property
.ToListAsync()Loads all chunks into memory for in-process similarity scoring
Scaling note: Loading all chunks into memory works fine for our seed data (~18 chunks, ~12 KB each). At enterprise scale (thousands of documents per company), you’d replace this with a vector database (pgvector, Qdrant, Pinecone) that does the similarity search in the database itself, still filtered by CompanyId.

Graceful empty handling:

if (chunks.Count == 0)
{
    logger.LogWarning("No document chunks found for CompanyId {CompanyId}", companyId);
    return "No knowledge base documents found for this company.";
}

Cosine Similarity — Rank by Relevance

RagService.cs — CosineSimilarity(), lines 41–51

For each chunk, deserialize the stored embedding from byte[] back to float[], then compute cosine similarity against the query vector:

// RagService.cs — score and rank
var results = chunks
    .Select(c => new
    {
        c.Title,
        c.Content,
        c.Source,
        Score = CosineSimilarity(
            queryVec,
            EmbeddingService.DeserializeEmbedding(c.Embedding))
    })
    .OrderByDescending(r => r.Score)
    .Take(topK);   // default topK = 3

The Cosine Similarity Formula

Measures the angle between two vectors. 1.0 = identical direction (perfect match), 0.0 = orthogonal (no relation), -1.0 = opposite.

private static float CosineSimilarity(float[] a, float[] b)
{
    float dot = 0, normA = 0, normB = 0;
    for (int i = 0; i < a.Length; i++)
    {
        dot   += a[i] * b[i];       // dot product
        normA += a[i] * a[i];       // squared magnitude of A
        normB += b[i] * b[i];       // squared magnitude of B
    }
    return dot / (MathF.Sqrt(normA) * MathF.Sqrt(normB));
}

// Formula: cos(θ) = (A · B) / (||A|| × ||B||)
// - Dot product measures how aligned the vectors are
// - Division by magnitudes normalizes it to [-1, 1]
Example Scoring
DocumentScoreWhy
Chicken Biryani recipe0.87Directly about chicken biryani with allergen info
Veg Thali recipe0.42Also food, but different dish
Samosa recipe0.38Related (food item) but less relevant
Operating Hours policy0.15Completely unrelated topic

Top-3 returns the biryani recipe, veg thali, and samosa. The policy is excluded because it scores too low.

Why not Euclidean distance? Cosine similarity compares direction, not magnitude. Two documents about “chicken biryani” of different lengths will have different magnitudes but similar directions. Cosine handles this naturally. For normalized embeddings (which OpenAI provides), cosine similarity and dot product are equivalent.

Claude now has the actual recipe data in its context. It reads the retrieved content and generates:

Claude’s Response

“No, the chicken biryani does not contain nuts. It’s made with basmati rice, chicken marinated in yogurt, ginger-garlic paste, and spices (red chilli, turmeric, garam masala, mint). The only allergen is dairy from the yogurt in the marinade. It’s garnished with fried onions and coriander.”

Why Tool-Driven, Not Always-On?

Some RAG systems run retrieval on every user message. We don’t. Claude decides when to search. Here’s why:

User messageNeeds RAG?What happens
“Show me today’s menu”NoClaude calls get_today_menu (structured data)
“Place an order for 2 biryanis”NoClaude calls place_order (action)
“Does biryani have nuts?”YesClaude calls search_knowledge (retrieval)
“What are the canteen hours?”YesClaude calls search_knowledge (retrieval)
“Hello!”NoClaude responds directly (no tool)

Benefits

  • Saves embedding API calls — “Place an order” doesn’t waste a ~50ms embedding request
  • Saves Claude context window — irrelevant chunks don’t eat into the 1024 max_tokens budget
  • Better answers — Claude isn’t confused by retrieved chunks about allergens when the user just wants to order
  • Transparent — the SSE events show the user “Searching knowledge base...” only when it actually searches

Tenant Isolation Deep-Dive

Tenant isolation is enforced at three levels:

LevelWhereHow
1. AuthenticationJWT tokencompanyId claim extracted from the signed JWT — can’t be forged
2. Database queryRagService.SearchAsyncWHERE CompanyId == companyId — pre-filter before loading
3. Schema constraintCanteenDbContextUnique index on (CompanyId, ContentHash) + foreign key with Restrict delete
Pre-filter, not post-filter. Company A’s chunks are never loaded into memory when Company B’s user searches. The WHERE clause runs in SQLite before any data leaves the database. Even if the similarity scoring code had a bug, it couldn’t leak cross-company data because the data was never in scope. 
// This is NOT what we do (post-filter — data leakage risk):
var allChunks = await db.DocumentChunks.ToListAsync();  // BAD: loads everything
var results = allChunks
    .Where(c => c.CompanyId == companyId)  // filters AFTER loading all companies
    .Select(c => new { ... });

// This IS what we do (pre-filter — tenant isolation):
var chunks = await db.DocumentChunks
    .Where(c => c.CompanyId == companyId)  // filters IN the database
    .Select(c => new { ... })
    .ToListAsync();

Serialization: float[] ↔ byte[]

SQLite stores embeddings as BLOB columns. We need to convert between float[] (what the API returns and what math uses) and byte[] (what SQLite stores):

// EmbeddingService.cs — zero-copy via Buffer.BlockCopy

// float[] → byte[] (for storing after ingestion)
public static byte[] SerializeEmbedding(float[] embedding)
{
    var bytes = new byte[embedding.Length * sizeof(float)];  // 3072 × 4 = 12,288 bytes
    Buffer.BlockCopy(embedding, 0, bytes, 0, bytes.Length);
    return bytes;
}

// byte[] → float[] (for retrieval-time comparison)
public static float[] DeserializeEmbedding(byte[] bytes)
{
    var floats = new float[bytes.Length / sizeof(float)];    // 12,288 / 4 = 3072 floats
    Buffer.BlockCopy(bytes, 0, floats, 0, bytes.Length);
    return floats;
}
DetailValue
Storage per chunk3072 floats × 4 bytes = 12 KB
MethodBuffer.BlockCopy — direct memory copy, no serialization overhead
Static methodsNo instance state needed — pure conversion functions
Why not JSON? Storing 3072 floats as a JSON array would take ~40 KB (numbers as text with commas). The binary BLOB is 12 KB — 3.3× smaller — and Buffer.BlockCopy is O(1) versus JSON parsing which is O(n). For 18 chunks the difference is negligible; for 10,000 it’s meaningful.

Interview Talking Points

Retrieval One-Liner

“Retrieval is tool-driven: Claude decides when a question needs document search, calls search_knowledge through the same agentic dispatch as ordering, which embeds the query via Azure OpenAI, runs cosine similarity over the company’s chunks with a CompanyId pre-filter for tenant isolation, and returns the top-3 results as context so Claude generates grounded answers instead of hallucinating.”

Likely Follow-Up Questions

Q: Why tool-driven instead of always-on retrieval?

“Place an order for 2 biryanis” doesn’t need RAG. By making retrieval a tool, Claude decides when to search. This avoids wasting embedding API calls, keeps the context window clean for non-knowledge queries, and shows the user transparent feedback (“Searching...”) only when it actually searches.

Q: How do you prevent cross-company data leakage?

Three levels: JWT carries the companyId claim (can’t forge), the database query pre-filters with WHERE CompanyId == companyId (data never leaves SQLite), and the schema has a unique index on (CompanyId, ContentHash). It’s a pre-filter, not a post-filter — chunks from other companies are never loaded into memory.

Q: Why cosine similarity instead of Euclidean distance?

Cosine compares direction, not magnitude. Two documents about “chicken biryani” of different lengths have different magnitudes but similar directions. For normalized embeddings (which OpenAI provides), cosine similarity and dot product are mathematically equivalent.

Q: How would you scale this beyond SQLite?

Replace the in-memory similarity loop with a vector database (pgvector, Qdrant, or Pinecone) that does approximate nearest neighbor search in the database itself, still filtered by CompanyId. The RagService.SearchAsync interface stays the same — only the implementation changes from “load all + LINQ” to a parameterized vector query.

Q: What happens if the knowledge base has nothing relevant?

Two cases: (1) no chunks at all for the company → returns “No knowledge base documents found” and Claude tells the user; (2) chunks exist but all score low → Claude still gets them but recognizes they’re not useful and says “I don’t have specific information about that.” Claude’s judgment handles the threshold, not a hardcoded cutoff.
