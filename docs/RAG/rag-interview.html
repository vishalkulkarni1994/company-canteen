Retrieval-Augmented Generation (RAG)

An interview guide explaining the RAG pattern — where relevant documents are retrieved via vector similarity search and injected into the LLM's context to ground answers in real knowledge. Covers architecture, embedding choices, chunking strategy, the full retrieval pipeline, annotated code walkthrough, and 15+ interview Q&A.

What is RAG?

Retrieval-Augmented Generation is a pattern where an LLM's response is grounded in externally retrieved documents rather than relying solely on its training data. Before the model generates an answer, the system searches a knowledge base for relevant content and injects it into the prompt as context.

Without RAG hallucination risk

User: "Does the paneer tikka contain nuts?"

Claude answers from training data — it doesn't know your recipes. It might hallucinate or say "I don't know."

With RAG grounded

User: "Does the paneer tikka contain nuts?"

System retrieves the paneer tikka recipe (ingredients: paneer, bell peppers, yogurt, spices — no nuts). Claude answers accurately from real data.

The core formula

Augmented Prompt = System Prompt + Retrieved Documents + User Question

The LLM never sees the vector store or the search process. It just gets a richer prompt with relevant context already included.

Key insight: RAG doesn't change the model — it changes the input. The model is the same Claude Haiku you'd call without RAG. The magic is in what you put in front of it.

Why RAG in our canteen app?

Our chat assistant already handles structured data via tool calling (menu items, orders, stock from the database). But there are questions it can't answer because the information doesn't exist in any database table:

Tool calling handles structured

  • "What's on the menu today?"
  • "Place an order for 2 biryanis"
  • "What's my order status?"

All answered by querying MenuItems, Orders, DailyStocks tables.

RAG handles unstructured

  • "Does the biryani contain nuts?"
  • "What's the cancellation policy?"
  • "Is the cold coffee vegan?"
  • "What are canteen hours during holidays?"

Answered from recipe documents and policy/FAQ text that doesn't fit in relational columns.

The decision rule: If the answer lives in a database column, use tool calling or Text-to-SQL. If the answer lives in a document (free-form text, recipes, policies, manuals), use RAG.

Design decisions

Embedding model

OptionDimensionsCostOur choice
text-embedding-3-large via Azure OpenAI 3,072 $0.13 / 1M tokens selected
text-embedding-3-small via OpenAI 1,536 $0.02 / 1M tokens cheaper alternative
voyage-3-lite via Voyage AI 512 $0.02 / 1M tokens Anthropic partner
all-MiniLM-L6-v2 local ONNX 384 Free offline option

Why Azure OpenAI? Enterprise-grade managed endpoint with SLA, regional deployment, and API key management. text-embedding-3-large gives 3,072 dimensions for best retrieval quality. For our small corpus the extra dimensions don't hurt latency or storage. In production with millions of documents, you'd benchmark small vs large and consider dimensionality reduction.

Interview talking point: "We intentionally use a different provider for embeddings (Azure OpenAI) than for generation (Anthropic Claude). This is a real-world pattern — embedding and generation are independent capabilities, and you should pick the best tool for each job."

Vector store

OptionPersistenceSearch typeOur choice
SQLite (BLOB column) Persistent, same DB Exact (brute-force cosine) selected
In-memory List<> Lost on restart Exact cosine rejected
Qdrant / Pinecone Persistent, separate service ANN (HNSW) overkill
pgvector (PostgreSQL) Persistent ANN (IVFFlat / HNSW) production option

Why SQLite? We already use it. Embeddings persist across restarts. For ~100 documents, brute-force cosine similarity is sub-millisecond. No new infrastructure needed. At scale, swap to pgvector or Qdrant — the application code stays the same, only the storage layer changes.

Chunking strategy

Our documents are naturally pre-chunked:

  • Recipes: one chunk per recipe (name + ingredients + allergens + prep method) — each is a coherent semantic unit under ~500 tokens
  • Policies: one chunk per FAQ entry or policy section

Interview talking point: "We didn't need recursive text splitting because each document was already a coherent unit. Chunking strategy should match your document structure — for a large PDF you'd use recursive splitting with overlap, but for discrete recipes and FAQ entries, one chunk per document preserves context perfectly."

Integration point

RAG is exposed as a tool inside the existing ChatService. When the user asks a knowledge question, Claude calls a search_knowledge tool that performs vector search and returns relevant document chunks. This means:

  • The same conversation can seamlessly mix tool calling (orders, menu) with RAG (recipes, policies)
  • Claude decides when to retrieve — it doesn't search for every message, only when it needs knowledge
  • No new API endpoint needed — works through the existing chat interface

Step-by-step walkthrough

Here's what happens when a user asks "Does the chicken biryani contain nuts?"

  1. User sends message

    The message arrives at ChatController and flows into ChatService with the full conversation history.

  2. Claude receives the message + tool definitions

    Claude sees the user question plus the available tools: get_today_menu, place_order, and the new search_knowledge. It decides this is a knowledge question and calls search_knowledge with query "chicken biryani nuts allergens ingredients".

  3. Query embedding

    RagService sends the search query to Azure OpenAI's text-embedding-3-large endpoint. Returns a 3,072-dimensional vector.

  4. Vector search

    The service loads all document embeddings from the DocumentChunks SQLite table, computes cosine similarity against the query vector, and returns the top-K (default: 3) most similar chunks.

    cosine_similarity(query_vector, doc_vector) =
    dot(q, d) / (||q|| * ||d||)
  5. Return context to Claude

    The top-K chunks are returned as the tool result. For this query, the top match is the Chicken Biryani recipe: "Ingredients: basmati rice, chicken, yogurt, onions, ginger, garlic, biryani spices, saffron, ghee. Allergens: dairy (yogurt, ghee). No nuts."

  6. Claude generates grounded answer

    Claude reads the retrieved recipe and responds: "No, the chicken biryani does not contain nuts. Its ingredients are basmati rice, chicken, yogurt, onions, ginger, garlic, biryani spices, saffron, and ghee. Note that it does contain dairy (yogurt and ghee)."

Key point: Claude decided on its own to call search_knowledge. If the user had asked "Show me today's menu" instead, Claude would have called get_today_menu. The agent picks the right tool based on the question.

RAG service

public class RagService
{
    public async Task<string> SearchAsync(string query, int companyId, int topK = 3)
    {
        // 1. Embed the query
        float[] queryVec = await _embedding.EmbedAsync(query);

        // 2. Load all document embeddings for this company
        var chunks = await _db.DocumentChunks
            .Where(c => c.CompanyId == companyId)
            .ToListAsync();

        // 3. Compute cosine similarity and rank
        var results = chunks
            .Select(c => new {
                c.Title, c.Content, c.Source,
                Score = CosineSimilarity(queryVec, DeserializeEmbedding(c.Embedding))
            })
            .OrderByDescending(r => r.Score)
            .Take(topK);

        // 4. Format as context string for Claude
        return string.Join("\n\n", results.Select(r =>
            $"[{r.Source}: {r.Title}] (relevance: {r.Score:F2})\n{r.Content}"));
    }

    private static float CosineSimilarity(float[] a, float[] b)
    {
        float dot = 0, normA = 0, normB = 0;
        for (int i = 0; i < a.Length; i++)
        {
            dot += a[i] * b[i];
            normA += a[i] * a[i];
            normB += b[i] * b[i];
        }
        return dot / (MathF.Sqrt(normA) * MathF.Sqrt(normB));
    }
}

Document types

Recipe documents RAG

Each recipe is one chunk containing:

  • Name and description
  • Full ingredient list
  • Allergen information
  • Dietary tags (vegan, gluten-free)
  • Preparation notes
  • Nutritional info (calories, protein)

Policy / FAQ documents RAG

Each policy section is one chunk:

  • Cancellation / refund policy
  • Operating hours (regular, holidays)
  • Ordering limits and rules
  • Payment methods accepted
  • Hygiene and food safety certifications
  • Bulk / meeting order process

What NOT to put in RAG: Menu items, prices, stock, orders, and bills are structured data that changes frequently. They belong in the database, accessed via tool calling or Text-to-SQL. RAG is for semi-static knowledge documents.

Interview Q&A

What is RAG and why do you need it?

RAG grounds LLM answers in external knowledge. Without it, the model relies on training data and can hallucinate about domain-specific facts. In our canteen app, Claude doesn't know our actual recipes or policies from training — RAG injects the real documents so it can answer accurately.

Why did you use a different provider for embeddings (OpenAI) vs generation (Claude)?

Embedding and generation are independent capabilities. We picked text-embedding-3-large from Azure OpenAI because it offers 3,072 dimensions with excellent retrieval quality. Claude doesn't offer an embedding API — Anthropic recommends Voyage AI as a partner, but OpenAI's embeddings are industry-standard and well-documented. Using different providers is a common production pattern.

Why text-embedding-3-large instead of small? Isn't it overkill?

For ~100 documents, yes, small would work fine. We chose large because: (1) higher recall quality matters more than cost at our scale, (2) the extra dimensions don't hurt performance for a small corpus, and (3) it shows understanding of the quality/cost tradeoff. In production with millions of documents, you'd benchmark both and potentially use dimensionality reduction (OpenAI supports reducing 3,072 to 256 dims via Matryoshka representation).

Why store vectors in SQLite instead of a dedicated vector database?

Our corpus is ~100 documents. Brute-force cosine similarity over 100 vectors takes under 1ms. Adding Qdrant or Pinecone would introduce infrastructure complexity (Docker, cloud service) for zero benefit at this scale. The application code is abstracted behind RagService — swapping to pgvector or Qdrant later means changing one class, not the architecture.

How does cosine similarity work?

Cosine similarity measures the angle between two vectors, ignoring magnitude. It's the dot product of the two vectors divided by the product of their magnitudes. A score of 1.0 means identical direction (semantically identical), 0 means orthogonal (unrelated), and -1 means opposite. For normalized embeddings (which OpenAI returns), cosine similarity equals the dot product.

cos(A, B) = (A · B) / (||A|| × ||B||)
// Range: -1 to 1 (practically 0 to 1 for text embeddings)
What's the difference between exact search and ANN (approximate nearest neighbor)?

Exact search compares the query vector against every stored vector. O(n) per query. Perfect for small corpora (<10K docs). ANN (used by Qdrant, Pinecone, pgvector) builds an index (HNSW, IVFFlat) that finds approximate nearest neighbors in O(log n). Trades a small accuracy loss (~1-5%) for massive speed gains. Essential above ~100K documents.

What if the right document doesn't appear in the top-K results?

This is the core RAG recall problem. Solutions ranked by impact:

  1. Re-ranking: Retrieve top-30 cheaply, then run a cross-encoder reranker (Cohere Rerank, ColBERT) to re-score and keep top-5. Cross-encoders attend to query-document pairs jointly, catching matches cosine similarity misses.
  2. Hybrid search: Combine dense embeddings with BM25 (keyword search) using Reciprocal Rank Fusion. Catches exact-term matches that embeddings underweight.
  3. Query transformation: Use HyDE (generate a hypothetical answer, embed that) or multi-query (rephrase the question 3-4 ways, union results).
  4. Better chunking: Smaller chunks with overlap, or semantic chunking. Index small chunks but attach parent context at retrieval time.
What's chunking and why does it matter?

Chunking splits large documents into smaller pieces for embedding. It matters because: (1) embedding models have token limits (8K for text-embedding-3), (2) smaller chunks are more semantically focused — a whole book would dilute the signal, and (3) you want to retrieve only the relevant part, not an entire document. Common strategies: fixed-size with overlap, recursive (split on paragraphs, then sentences), semantic (split on topic shifts). We use document-level chunking because each recipe/FAQ entry is already a coherent unit under 500 tokens.

How do you handle document updates?

We hash each document's content. On startup (or when an admin updates a recipe), the ingestion service compares hashes against stored chunks. Changed documents get re-embedded and upserted. Deleted documents have their chunks removed. This avoids re-embedding the entire corpus on every restart.

What's the difference between RAG and fine-tuning?

RAG adds knowledge at query time by injecting retrieved documents into the prompt. The model weights don't change. Best for: factual recall, frequently changing data, citing sources. Fine-tuning changes the model's weights by training on your data. Best for: changing the model's behavior/style, learning domain-specific patterns. RAG is cheaper, faster to update, and doesn't risk catastrophic forgetting. Fine-tuning is more permanent and better for behavioral changes. Most teams start with RAG.

How do you prevent hallucination even with RAG?

RAG reduces hallucination but doesn't eliminate it. Defenses: (1) Instruct the model in the system prompt: "Answer only from the provided context. If the information isn't in the context, say you don't know." (2) Include relevance scores — if the top result's similarity is below a threshold (e.g., 0.3), tell the model no relevant documents were found. (3) Ask the model to cite which document it's drawing from. (4) Post-generation validation: check if the answer references information not present in the retrieved chunks.

What's the embedding dimension tradeoff?

Higher dimensions capture more semantic nuance but cost more storage and compute. text-embedding-3-small (1,536 dims) vs large (3,072 dims): large is ~2x storage and slightly slower similarity computation, but better at distinguishing subtle differences. OpenAI's Matryoshka representation lets you truncate large embeddings to 256 dims with minimal quality loss — useful for production systems that need fast approximate search.

Why is RAG exposed as a tool rather than always running?

Not every question needs document retrieval. "Place an order for 2 biryanis" doesn't need RAG — it needs the place_order tool. By exposing RAG as a search_knowledge tool, Claude decides when to use it. This avoids wasting embedding API calls and context window space on irrelevant retrievals. It also lets the same conversation seamlessly combine tool calling (actions) with RAG (knowledge).

How would you scale this to millions of documents?

Three changes: (1) Vector database: swap SQLite for pgvector (PostgreSQL) or Qdrant, which use HNSW indexes for O(log n) approximate search. (2) Chunking pipeline: move from startup ingestion to an async pipeline (queue + worker) that processes document changes incrementally. (3) Re-ranking: add a cross-encoder re-ranker between retrieval and generation. Retrieve top-50 with ANN, re-rank to top-5 with a model like Cohere Rerank. The RAG service interface stays identical — only the implementation changes.

What about multi-tenancy in RAG?

Each document chunk has a CompanyId. The vector search filters by CompanyId before computing similarity — Company A's users never see Company B's recipes. This matches our existing multi-tenant pattern across the app. In a production vector database, you'd use metadata filtering (Qdrant) or row-level security (pgvector) for the same isolation.

Production considerations

What we implemented

  • Multi-tenant isolation: CompanyId filter on every vector search
  • Persistent storage: SQLite BLOB column survives restarts
  • Content hashing: Only re-embed changed documents on startup
  • Relevance threshold: Don't return chunks below a minimum similarity score
  • Graceful degradation: If the embedding API is down, the chat still works (tool calling still functions, just no knowledge retrieval)

What we'd add at scale

  • Re-ranking: Cross-encoder reranker (Cohere Rerank) between retrieval and generation
  • Hybrid search: Combine vector similarity with BM25 keyword search
  • Async ingestion: Queue-based pipeline for processing document updates
  • Caching: Cache embeddings for frequent queries (LRU cache on the embedding service)
  • Monitoring: Track retrieval quality — relevance scores, user feedback, failed retrievals
  • Evaluation: Build a test set of question/answer pairs to measure retrieval recall and generation accuracy

Common RAG pitfall: Don't put structured data into RAG. Menu prices, stock levels, and order history change constantly and are already perfectly served by SQL queries. RAG is for semi-static knowledge documents. Mixing these leads to stale answers and unnecessary complexity.
