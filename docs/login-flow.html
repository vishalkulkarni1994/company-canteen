How a person logs in

From the sign-in page to the home screen: every endpoint, every component, what each one does and how it does it. Built with .NET 10, React, and SQLite.

Overview

Login uses an email and a password stored in SQLite. The .NET API checks them and hands back a JSON Web Token (JWT): a signed note that says "this is user X with role Y". The browser keeps the token and attaches it to every later request. The server never keeps a session in memory; it verifies the signature on each request through ASP.NET's JwtBearer middleware.

Frontend client/

React 19 + TypeScript + Vite. Files: App.tsx, main.tsx, pages/LoginPage.tsx, pages/HomePage.tsx, api/auth.ts, context/AuthContext.tsx.

Backend server/

.NET 10 Web API with controllers. Files: Program.cs, Controllers/AuthController.cs, Models/User.cs, Models/LoginRequest.cs, Data/CanteenDbContext.cs, Services/AuthService.cs.

Data SQLite

The Users table: Id (int, PK), Email (unique), Name, PasswordHash, Role, CreatedAt.

Login at a glance

One successful sign-in, left to right. Solid arrows are calls, dashed arrows are replies. The numbers match the step-by-step walkthrough.

Step by step: a fresh sign-in

  1. Browser opens the app

    main.tsx mounts <App /> inside StrictMode. AuthProvider checks localStorage for a saved auth state. With nothing saved, user is null, so the router redirects to /login and renders LoginPage.

  2. User fills in the form and presses Sign In

    Each keystroke updates the email or password state via controlled inputs. The email field has type="email" and required; the password field has minLength={6}. A toggle switches between Sign In and Register modes. Submitting calls handleSubmit(e).

  3. handleSubmit() calls the API

    It sets loading = true (the button shows "..."), clears any old error, and calls login(email, password) from api/auth.ts. This sends a POST to http://localhost:5230/api/auth/login with a JSON body { email, password }.

  4. AuthController receives the request

    ASP.NET routes the request to the Login action in AuthController. The [FromBody] attribute deserializes the JSON into a LoginRequest record. It queries SQLite via EF Core: db.Users.FirstOrDefaultAsync(u => u.Email == req.Email).

  5. Password verification

    If the user exists, BCrypt.Net.BCrypt.Verify(req.Password, user.PasswordHash) re-hashes the typed password with the stored salt and compares. If no user is found or the password is wrong, the endpoint returns 401 Unauthorized.

  6. Token generation

    AuthService.GenerateToken(user) creates a JWT with four claims (NameIdentifier, Email, Name, Role), signs it with HMAC-SHA256 using the key from appsettings, and sets an 8-hour expiry. It also sets the Issuer and Audience.

  7. The response travels back

    The controller action returns Ok(new AuthResponse(...)) which becomes a 200 OK with { token, email, name, role }. The api/auth.ts client parses the JSON and returns it to LoginPage.

  8. The app stores the auth state and navigates

    setAuth(res) writes the token and user info to localStorage under the key auth as a JSON string, and updates the React context. navigate("/") sends the user to the home page. The ProtectedRoute wrapper sees user is no longer null and renders HomePage.

Backend: every function

All paths are under server/.

Program.cs startupProgram.cs

WhatConfigures services and the middleware pipeline. Contains no endpoint logic.

HowRegisters AddControllers(), CanteenDbContext with the SQLite connection string, AuthService as a singleton, and the JWT Bearer authentication scheme. Configures CORS to allow the Vite dev server at http://localhost:5173. On startup, calls db.Database.EnsureCreated() to auto-create the SQLite file and tables. Endpoints are discovered via app.MapControllers().

Controllers/AuthController.cs auth endpoints

An [ApiController] routed at api/[controller], which resolves to /api/auth. Dependencies (CanteenDbContext and AuthService) are injected via the primary constructor.

[HttpPost("register")] RegisterAuthController.cs

WhatCreates a new user account and returns a token.

HowAccepts a [FromBody] RegisterRequest. Checks if the email already exists. If so, returns Conflict(). Otherwise hashes the password with BCrypt, creates the User entity with role "Employee", saves to SQLite, generates a JWT, and returns the AuthResponse.

var user = new User
{
    Email = req.Email,
    PasswordHash = BCrypt.Net.BCrypt.HashPassword(req.Password),
    Name = req.Name
};
db.Users.Add(user);
await db.SaveChangesAsync();
var token = auth.GenerateToken(user);
return Ok(new AuthResponse(token, user.Email, user.Name, user.Role));
[HttpPost("login")] LoginAuthController.cs

WhatChecks credentials and issues a token. This is the heart of the login flow.

HowAccepts a [FromBody] LoginRequest. Looks up the user by email. If not found or the password doesn't verify, returns Unauthorized() with no message distinguishing the two cases. On success, generates a token and returns the AuthResponse.

var user = await db.Users.FirstOrDefaultAsync(u => u.Email == req.Email);
if (user is null || !BCrypt.Net.BCrypt.Verify(req.Password, user.PasswordHash))
    return Unauthorized();

var token = auth.GenerateToken(user);
return Ok(new AuthResponse(token, user.Email, user.Name, user.Role));
[HttpGet("me")] [Authorize] MeAuthController.cs

WhatReturns the currently signed-in user's info from the token claims.

HowProtected by the [Authorize] attribute. The JWT Bearer middleware validates the token before the action runs. The action reads the claims from the inherited User property (a ClaimsPrincipal). No database call is made — it trusts the token.

AuthService.GenerateToken(user)Services/AuthService.cs

WhatCreates the signed JWT.

HowBuilds a SymmetricSecurityKey from the configured Jwt:Key. Adds four claims: NameIdentifier (user id), Email, Name, and Role. Sets issuer, audience, and an 8-hour expiry. Signs with HmacSha256 and returns the serialized token string.

var claims = new[]
{
    new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
    new Claim(ClaimTypes.Email, user.Email),
    new Claim(ClaimTypes.Name, user.Name),
    new Claim(ClaimTypes.Role, user.Role)
};
var token = new JwtSecurityToken(
    issuer: config["Jwt:Issuer"],
    audience: config["Jwt:Audience"],
    claims: claims,
    expires: DateTime.UtcNow.AddHours(8),
    signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));
CanteenDbContextData/CanteenDbContext.cs

WhatEF Core context with a unique index on User.Email.

HowUses the primary constructor to accept DbContextOptions. The OnModelCreating override creates a unique index on the email column so duplicate registrations are caught at the database level.

User entityModels/User.cs

WhatThe database model for a user account.

HowProperties: Id (int, auto-increment PK), Email, PasswordHash, Name, Role (defaults to "Employee"), CreatedAt (defaults to DateTime.UtcNow).

Frontend: every page and function

All paths are under client/src/.

App.tsx routing and auth guards

AppApp.tsx

WhatSets up the router with two routes: /login and /.

HowWraps everything in AuthProvider and BrowserRouter. Two guard components control access:

  • ProtectedRoute: if user is null, redirects to /login. Otherwise renders children.
  • GuestRoute: if user exists, redirects to /. Prevents signed-in users from seeing the login form.

context/AuthContext.tsx auth state management

AuthProviderAuthContext.tsx

WhatProvides the auth state and actions to the entire app via React context.

HowOn mount, reads localStorage key auth for a previously saved session (wrapped in try/catch in case the stored value is malformed). Exposes three values:

  • user — the current auth state (token, email, name, role) or null.
  • setAuth(res) — saves the auth response to state and localStorage.
  • logout() — clears the state and removes localStorage. No server call: the server keeps no session.

pages/LoginPage.tsx the sign-in page

LoginPageLoginPage.tsx

WhatShows a form that toggles between sign-in and registration modes.

HowSix pieces of state: isRegister (toggle), email, password, name (register only), error, loading. Both modes share the same form; the name field appears only in register mode. On submit:

  • Calls login() or register() from api/auth.ts.
  • On success: setAuth(res) saves the session, navigate("/") goes to the home page.
  • On failure: the error message shows in red above the form. The button re-enables via finally.

api/auth.ts talking to the server

login(email, password) and register(email, password, name)api/auth.ts

WhatSend credentials to the API and return the AuthResponse.

HowPlain fetch calls to http://localhost:5230/api/auth/login and /register. Both send JSON, check res.ok, and throw on failure. The error message from the server (if JSON) is preserved in the thrown error.

const res = await fetch(`${API}/login`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ email, password }),
});
if (!res.ok) throw new Error("Invalid credentials");
return res.json();

The token itself

A JWT is three base64url pieces joined by dots: header.payload.signature. The values below illustrate the shape.

Header

{
  "alg": "HS256",
  "typ": "JWT"
}

Payload (claims)

{
  "http://.../nameidentifier": "1",
  "http://.../emailaddress": "alice@co.com",
  "http://.../name": "Alice",
  "http://.../role": "Employee",
  "exp": 1791325015,
  "iss": "CanteenApi",
  "aud": "CanteenApp"
}

Signature

HMAC-SHA256(
  base64url(header) + "." +
  base64url(payload),
  Jwt:Key from appsettings
)
ClaimMeaningUsed by
NameIdentifierThe user's database idIdentifies the user on protected endpoints
EmailThe user's email addressReturned by /api/auth/me
NameThe user's display nameReturned by /api/auth/me
RoleEmployee (default)Used for role-based authorization
expExpiry: 8 hours from issueChecked by JWT Bearer middleware
issCanteenApiValidated by JWT Bearer middleware
audCanteenAppValidated by JWT Bearer middleware

.NET uses full URI claim types (e.g. http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress) by default, not short names like sub or role. This is a .NET convention; the token is still a standard JWT.

The payload is encoded, not encrypted: anyone holding the token can read it. What they cannot do is change it, because the signature would no longer match.

Failure cases

What goes wrongWhere it is caughtWhat the user sees

Token expiredJWT Bearer middleware rejects the requestProtected endpoints return 401; frontend should redirect to login

Wrong-password and unknown-email both return the same 401 with no body. This is intentional: it stops anyone from discovering which emails have accounts.

Security notes

What is in place

  • Passwords stored only as BCrypt hashes, never in plain text or in any API response.
  • Signature, expiry, issuer and audience checked on every request by ASP.NET middleware.
  • Algorithm implicitly pinned to HMAC variants by the SymmetricSecurityKey type.
  • CORS restricted to the frontend origin.
  • Identical error for wrong-password and unknown-email.
  • Unique index on email prevents duplicate accounts at the database level.

Known gaps

Worth fixing before real users.

  • No startup guard. The API does not validate that Jwt:Key is present or strong enough at startup.
  • Stale tokens. A token is trusted for 8 hours. Deactivating a user does not revoke existing tokens.
  • localStorage storage. Injected script (XSS) could read the token. An httpOnly cookie is safer.
  • No rate limit on login attempts.
  • No session restore check. The frontend trusts localStorage on load without calling /api/auth/me to verify the token is still valid.
  • No email normalization. The API does not trim or lowercase emails before lookup.
  • No token refresh. After 8 hours the user must sign in again.
  • HTTPS is required in any real deployment, or the password travels in clear text.

Running it

Backend

cd server
dotnet run

Starts on http://localhost:5230. SQLite file canteen.db is auto-created on first run.

Frontend

cd client
npm run dev

Starts on http://localhost:5173. Open this URL in a browser to use the app.

Start the backend first. The frontend calls the API directly at localhost:5230 — there is no proxy configured in Vite, so the backend must be running for login to work.
