SSE streaming with agentic tool calling

Real-time token-by-token streaming from Claude through the .NET backend to the React frontend, using Server-Sent Events. Text deltas, tool-start, and tool-done events stream as they happen — no waiting for the full response. The agentic tool-use loop runs between streaming rounds.

Overview

The non-streaming chat endpoint (POST /api/chat) waits for Claude to finish all tool rounds before returning the complete response. The streaming endpoint (POST /api/chat/stream) sends events as they happen — text characters appear immediately, and tool calls show live status indicators.

Non-streaming before

  • User sends message
  • Waits 2–5 seconds (all tool rounds)
  • Gets complete response at once
  • No feedback during processing

Streaming after

  • User sends message
  • Text appears token-by-token (~50ms per token)
  • Tool calls show live status (⟳ running → ✓ done)
  • Multi-round loops stream each round incrementally

The implementation spans four layers, each with both a non-streaming and streaming path:

LayerNon-streamingStreaming
IClaudeMessageClient SendAsync() → ClaudeResponse SendStreamAsync() → IAsyncEnumerable<ClaudeStreamEvent>
ClaudeApiService SendAsync() with agentic loop SendStreamAsync() with streaming agentic loop
ChatService SendMessage() SendMessageStream() (passthrough)
ChatController POST /api/chat → JSON response POST /api/chat/stream → SSE stream

Why SSE

Server-Sent Events is the right transport here because the data flow is strictly one-directional: server to client. There is no need for the client to send messages during a stream — it sends one HTTP POST, then reads events until the stream ends.

SSE chosen

  • Regular HTTP — works through proxies, CDNs, load balancers
  • Native browser support via EventSource (or fetch + ReadableStream)
  • Automatic reconnection built into the protocol
  • Text-based, easy to debug with browser DevTools
  • What Claude's own API uses for streaming

WebSocket not needed

  • Full-duplex — unnecessary for a request/response chat
  • Binary framing adds complexity
  • Connection upgrade can fail behind some proxies
  • Requires SignalR or raw WS library
  • Overkill when data flows one way

SSE format. Each event is a line starting with data: followed by JSON, terminated by \n\n. The stream ends with data: [DONE]\n\n. This is the same format Claude's API uses, making the backend a near-transparent relay.

Wire protocol

The streaming endpoint sends three event types as JSON, each on a data: line:

EventJSON shapeWhen
text {"type":"text","text":"Hello"} Each text token from Claude (many per response)
tool_start {"type":"tool_start","tool":"get_today_menu"} Claude begins a tool call block
tool_done {"type":"tool_done","tool":"get_today_menu"} Tool execution completed (after DB query)
error {"type":"error","text":"Something went wrong."} Unrecoverable error during streaming
[DONE] literal string, not JSON Stream complete

Backend layers

Three C# layers collaborate to produce the SSE stream. Each layer uses IAsyncEnumerable<ClaudeStreamEvent> and yield return to pass events upstream without buffering.

Layer 1: HttpClaudeClient.SendStreamAsync

SendStreamAsyncSSE parser

File server/Services/HttpClaudeClient.cs

Sends a request with stream: true to Claude's API, reads the SSE response line-by-line, and yields typed events. Accumulates text and tool-input fragments across content_block_delta events, then yields a RoundComplete event with the fully assembled ClaudeResponse.

// Key: read headers only, don't buffer the full response
using var resp = await httpClient.SendAsync(request,
    HttpCompletionOption.ResponseHeadersRead, ct);

using var stream = await resp.Content.ReadAsStreamAsync(ct);
using var reader = new StreamReader(stream);

while (!reader.EndOfStream)
{
    var line = await reader.ReadLineAsync(ct);
    if (!line.StartsWith("data: ")) continue;
    var data = line["data: ".Length..];
    if (data == "[DONE]") break;

    var evt = JsonDocument.Parse(data).RootElement;
    var evtType = evt.GetProperty("type").GetString();

    switch (evtType)
    {
        case "content_block_start":
            // Begin text or tool_use block
            break;
        case "content_block_delta":
            // Accumulate text_delta or input_json_delta
            if (deltaType == "text_delta")
                yield return new ClaudeStreamEvent {
                    Type = StreamEventType.TextDelta,
                    Text = chunk
                };
            break;
        case "content_block_stop":
            // Finalize the block (add to blocks list)
            break;
        case "message_delta":
            // Extract stop_reason and output_tokens
            break;
        case "message_start":
            // Extract input_tokens
            break;
    }
}

// Final event: assembled ClaudeResponse for the agentic loop
yield return new ClaudeStreamEvent {
    Type = StreamEventType.RoundComplete,
    Response = new ClaudeResponse { ... }
};

Layer 2: ClaudeApiService.SendStreamAsync

SendStreamAsyncagentic loop

File server/Services/ClaudeApiService.cs

The streaming agentic loop. Iterates up to 10 rounds. Each round streams events from HttpClaudeClient, yielding TextDelta and ToolStart immediately to the caller. When RoundComplete arrives, it checks whether Claude wants tools — if so, executes them (yielding ToolDone), appends results, and continues the next round.

public async IAsyncEnumerable<ClaudeStreamEvent> SendStreamAsync(
    string query, ClaudeAgentDefinition agentDef,
    Func<string, JsonElement, Task<string>> dispatchTool,
    List<ChatMessage>? history = null,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    var messages = new List<object>();
    // ... build messages from history + query

    for (var round = 0; round < MaxToolRounds; round++)
    {
        ClaudeResponse? roundResponse = null;

        // Stream events from this round, yielding text/tool_start
        await foreach (var evt in client.SendStreamAsync(agentDef, messages, ct))
        {
            if (evt.Type == StreamEventType.RoundComplete)
                roundResponse = evt.Response;  // capture, don't yield
            else
                yield return evt;  // pass through to controller
        }

        if (roundResponse?.StopReason != "tool_use")
            break;  // Claude is done

        // Execute tools between rounds
        messages.Add(new { role = "assistant", content = /* ... */ });
        var toolResults = new List<object>();

        foreach (var block in roundResponse.Content.Where(b => b.Type == "tool_use"))
        {
            var toolResult = await dispatchTool(block.Name!, block.Input);
            yield return new ClaudeStreamEvent {
                Type = StreamEventType.ToolDone,
                ToolName = block.Name
            };
            toolResults.Add(new { type = "tool_result", tool_use_id = block.Id, content = toolResult });
        }

        messages.Add(new { role = "user", content = toolResults.ToArray() });
        // Loop continues → next round streams from Claude with tool results
    }
}

Layer 3: ChatController SSE endpoint

POST /api/chat/streamcontroller

File server/Controllers/ChatController.cs

Sets the text/event-stream content type, iterates the IAsyncEnumerable, maps each event to JSON, writes data: {json}\n\n, and flushes after every event. Sends data: [DONE]\n\n when the stream ends.

[HttpPost("stream")]
public async Task Stream([FromBody] ChatRequest req)
{
    Response.ContentType = "text/event-stream";
    Response.Headers.CacheControl = "no-cache";
    Response.Headers.Connection = "keep-alive";

    var ct = HttpContext.RequestAborted;

    await foreach (var evt in chatService.SendMessageStream(
        req.Message, userId, companyId.Value, req.History, ct))
    {
        var json = evt.Type switch
        {
            StreamEventType.TextDelta  => Serialize(new { type = "text", text = evt.Text }),
            StreamEventType.ToolStart  => Serialize(new { type = "tool_start", tool = evt.ToolName }),
            StreamEventType.ToolDone   => Serialize(new { type = "tool_done", tool = evt.ToolName }),
            _ => null
        };

        if (json == null) continue;
        await Response.WriteAsync($"data: {json}\n\n", ct);
        await Response.Body.FlushAsync(ct);
    }

    await Response.WriteAsync("data: [DONE]\n\n", ct);
    await Response.Body.FlushAsync(ct);
}

Three critical SSE headers. Content-Type: text/event-stream tells the browser this is an SSE stream. Cache-Control: no-cache prevents buffering by intermediate proxies. Connection: keep-alive keeps the TCP connection open for the duration of the stream.

Client-side SSE parsing

The React client uses fetch with a ReadableStream reader rather than the native EventSource API. This is because EventSource only supports GET requests — our endpoint is POST with a JSON body and an Authorization header.

streamChat()AsyncGenerator

File client/src/api/chat.ts

An async function* (AsyncGenerator) that POSTs to the stream endpoint, then reads chunks from the response body. Chunks may contain partial lines, so a buffer accumulates text and splits on newlines. Each data: line is parsed as JSON and yielded as a typed StreamEvent.

export async function* streamChat(
  message: string, history: ChatMessage[]
): AsyncGenerator<StreamEvent> {

  const res = await fetch(`${API}/stream`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
    },
    body: JSON.stringify({ message, history }),
  });

  const reader = res.body?.getReader();
  const decoder = new TextDecoder();
  let buffer = "";

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop() ?? "";

    for (const line of lines) {
      if (!line.startsWith("data: ")) continue;
      const data = line.slice(6);
      if (data === "[DONE]") { yield { type: "done" }; return; }
      yield JSON.parse(data) as StreamEvent;
    }
  }
}

TypeScript event types

export type StreamEvent =
  | { type: "text"; text: string }
  | { type: "tool_start"; tool: string }
  | { type: "tool_done"; tool: string }
  | { type: "error"; text: string }
  | { type: "done" };

Why AsyncGenerator? The async function* pattern lets the React component consume events with a clean for await loop. Each yield pauses the generator until the component is ready for the next event. This provides natural backpressure and keeps the parsing logic separate from the UI rendering.

Buffer handling

TCP chunks don't align with SSE event boundaries. A single reader.read() might return half a line, or three lines at once. The buffer-and-split approach handles this:

  1. Append the decoded chunk to a buffer string
  2. Split on \n — the last element may be incomplete
  3. lines.pop() removes the possibly-incomplete tail back into the buffer
  4. Process only complete lines (those that survived the split)

Streaming agentic loop

The key insight: streaming and tool calling work together seamlessly. Text tokens stream within a round, and tool execution happens between rounds. The user sees text appearing in real-time, then a tool status indicator, then more streaming text.

Multi-round timeline

A user says "order 2 chai for me". Claude first needs the menu (round 1), then places the order (round 2), then confirms (round 3):

  1. Round 1: Claude calls get_today_menu

    Client sees: tool_start "Checking today's menu..." → (server queries DB, ~20ms) → tool_done "✓ Checking today's menu"

  2. Round 2: Claude sees the menu and calls place_order

    Client sees: streaming text "I'll order 2 Masala Chai for you..." → tool_start "Placing your order..." → (server creates order, decrements stock) → tool_done "✓ Placing your order"

  3. Round 3: Claude confirms with final text

    Client sees: streaming text "Done! Order #42 placed. 2x Masala Chai — ₹40 total. Your order is in the queue!"

Event types (internal)

StreamEventTypeenum

File server/Services/IClaudeMessageClient.cs

public enum StreamEventType
{
    TextDelta,     // A chunk of text from Claude
    ToolStart,     // Claude is beginning a tool call
    ToolDone,      // Tool execution completed
    RoundComplete  // Internal: full response assembled (not sent to client)
}

RoundComplete is consumed internally by the agentic loop to reconstruct the full ClaudeResponse for message accumulation. It is never serialized to the client.

ToolStart vs ToolDone timing. ToolStart is emitted by HttpClaudeClient when Claude's SSE stream sends content_block_start for a tool_use block. ToolDone is emitted by ClaudeApiService after the tool actually executes (the DB query completes). This means the user sees "Checking today's menu..." before the database is even queried — maximum perceived responsiveness.

React chat UI

The ChatPage component consumes the streaming events and renders them in real-time. It maintains an array of DisplayMessage objects that grow as events arrive.

ChatPage.tsxReact

File client/src/pages/ChatPage.tsx

The component uses a for await loop over the streamChat() AsyncGenerator, dispatching each event type to a state update:

for await (const evt of streamChat(text.trim(), history)) {
  switch (evt.type) {
    case "text":
      // Append text chunk to the last assistant message
      setMessages(prev => {
        const next = [...prev];
        const last = { ...next[next.length - 1] };
        last.content += evt.text;
        next[next.length - 1] = last;
        return next;
      });
      break;

    case "tool_start":
      // Add tool event with status "running"
      setMessages(prev => {
        const next = [...prev];
        const last = { ...next[next.length - 1] };
        last.toolEvents = [
          ...(last.toolEvents ?? []),
          { tool: evt.tool, status: "running" },
        ];
        next[next.length - 1] = last;
        return next;
      });
      break;

    case "tool_done":
      // Update tool status from "running" to "done"
      setMessages(prev => {
        const next = [...prev];
        const last = { ...next[next.length - 1] };
        last.toolEvents = (last.toolEvents ?? []).map(t =>
          t.tool === evt.tool ? { ...t, status: "done" } : t
        );
        next[next.length - 1] = last;
        return next;
      });
      break;
  }
}

UI features

Suggestion chips

When the chat is empty, three suggestion buttons appear: "What's on the menu today?", "Order 2 chai for me", "What's the cheapest item available?" Clicking one sends that message immediately.

Tool status indicators

Tool events render above the message text: ⟳ Checking today's menu... (running, teal italic) or ✓ Checking today's menu (done, grey). Human-readable labels map tool names: get_today_menu → "Checking today's menu".

Streaming cursor

While waiting for the first text token, a blinking ● cursor shows the assistant is thinking. It disappears once text starts arriving.

JsonElement bug fix

A subtle serialization bug caused streaming to silently fail on the second agentic round. This is worth documenting because the failure mode was completely invisible.

The problem

When Claude calls get_today_menu, the tool has no input parameters. Claude's streaming API sends the content_block_start event with an empty input, then no input_json_delta events. In our SSE parser, inputJsonAccumulator remained empty.

The original code used default for the empty case:

// BUG: default(JsonElement) has ValueKind.Undefined
var inputElement = string.IsNullOrEmpty(inputJson)
    ? default                              // ← ValueKind.Undefined
    : JsonDocument.Parse(inputJson).RootElement;

default(JsonElement) has ValueKind = Undefined. This value was stored in the ContentBlock.Input property and added to the blocks list. When the agentic loop built the messages array for round 2, it serialized these blocks including the Undefined JsonElement — and JsonSerializer.Serialize throws on ValueKind.Undefined.

The fix

// FIX: parse an empty object to get ValueKind.Object
var inputElement = string.IsNullOrEmpty(inputJson)
    ? JsonDocument.Parse("{}").RootElement  // ← ValueKind.Object
    : JsonDocument.Parse(inputJson).RootElement;

Why it was hard to find

  • The first Claude API call succeeded — the stream worked fine
  • The crash happened during serialization for the second call, not during parsing
  • The controller's generic catch (Exception) returned {"type":"error","text":"Something went wrong."} — no stack trace in the client
  • The network response showed: tool_start → tool_done → error (no text events). This looked like Claude refused to respond, not a serialization bug

Lesson. When using JsonElement as a DTO field in C#, never use default. Always parse an explicit value (JsonDocument.Parse("{}").RootElement) to ensure the element has a valid ValueKind. The non-streaming path didn't hit this because the non-streaming response includes the full input property as a JSON object — the empty-input case only manifests in the streaming SSE parser.

Error handling

Errors can occur at three points: the Claude API call, tool execution, or client-side parsing. Each layer handles errors differently.

LayerError typeHandling
HttpClaudeClient Claude API returns non-2xx Throws exception with status code and body
ChatController OperationCanceledException Silently swallowed (client disconnected)
ChatController Any other exception Writes {"type":"error","text":"Something went wrong."} to the stream
streamChat() HTTP 401 Yields {"type":"error","text":"Please log in again."}
streamChat() Malformed JSON in SSE line Silently skipped (try { JSON.parse } catch {})
ChatPage Network error or stream breaks Shows "Connection lost. Please try again." in the message bubble

Cancellation. The controller passes HttpContext.RequestAborted as the CancellationToken all the way down to the Claude API call. If the user navigates away mid-stream, the token fires, the StreamReader throws OperationCanceledException, and the controller catches it silently. No wasted API calls or open connections.
