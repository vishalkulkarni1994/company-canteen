System Design of a Multi-Tenant Company Canteen

A complete walkthrough of how to design a real-world food ordering platform — from high-level architecture to database schemas, API contracts, authentication, AI-powered features, and scalability trade-offs.

Fundamentals

What Is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data flows of a system to satisfy specified requirements. In interviews, it tests your ability to think at scale about real-world engineering problems.

In an interview context: You're given a vague problem ("Design a food ordering system for corporate canteens") and expected to work through requirements, propose an architecture, design data models, define APIs, and discuss trade-offs — all within 45–60 minutes. The goal isn't a perfect answer; it's demonstrating structured thinking.

The System Design Framework

1
Clarify Requirements

Ask questions. Who are the users? What's the scale? What are the must-have features vs. nice-to-haves? Functional requirements (ordering, menus) vs. non-functional (latency, availability, consistency).

2
Estimate Scale

How many users? Orders per day? Data size? Read-to-write ratio? These numbers drive every architectural decision — a system serving 100 users is designed very differently from one serving 100,000.

3
Define High-Level Architecture

Draw the big boxes: clients, load balancers, API servers, databases, caches, message queues, third-party services. Show how data flows between them.

4
Design Core Components

Dive deep into 2–3 critical components. Design database schemas, define API contracts, work out state machines for order status, discuss authentication strategy.

5
Address Bottlenecks & Trade-offs

Discuss scaling strategies, caching, database indexing, consistency vs. availability. Every choice has a trade-off — show you understand both sides.

Key Concepts That Appear in Every Design

↔

Horizontal vs. Vertical Scaling

Vertical: bigger machine (more CPU/RAM). Horizontal: more machines behind a load balancer. Horizontal is harder but gives better availability and fault tolerance.

⚡

CAP Theorem

In a distributed system, you can only guarantee two of three: Consistency, Availability, Partition tolerance. Most web apps choose AP with eventual consistency.

📦

Caching

Store frequently accessed data in memory (Redis, Memcached). Reduces database load and latency. Key decisions: cache invalidation strategy, TTL, what to cache vs. what to always fetch fresh.

🔒

Authentication & Authorization

Who are you (AuthN) vs. what can you do (AuthZ). JWT tokens, OAuth, RBAC (Role-Based Access Control). Stateless tokens scale well but can't be revoked easily.

🗄

Database Design

SQL vs. NoSQL, normalization, indexing, sharding. SQL gives you ACID transactions (important for orders + money). NoSQL gives flexible schemas and horizontal scaling.

💬

Real-Time Communication

WebSockets for bidirectional. Server-Sent Events (SSE) for server-to-client streaming. Long polling as a fallback. Choose based on whether the client needs to push data back.

Data Layer

Database Design

The database is normalized to 3NF with six core entities. Every table is scoped to a company through direct or transitive foreign keys, enabling the multi-tenant data isolation model.

Entity-Relationship Diagram

Entity-relationship diagram — Company is the tenant root; all data flows through it

Key Design Decisions

Soft Deletes for Menu Items

Menu items use an IsActive flag instead of hard deletes. This preserves order history — if you delete "Chicken Biryani" after 500 people ordered it, those order records still reference a valid item.

Daily Stock as a Separate Entity

Stock is date-scoped (MenuItemId + Date unique constraint) rather than a field on MenuItem. This lets admins set stock per day and keeps a historical record.

Nullable CompanyId on User

SuperAdmin users have CompanyId = null because they operate across all companies. Regular users always belong to exactly one company.

Price Snapshot on OrderItem

UnitPrice is captured at order time, so price changes don't affect historical orders. Subtotal is computed (Quantity * UnitPrice), not stored.

Order State Machine

Orders follow a strict state machine with only forward transitions. This prevents invalid states and makes the kitchen workflow predictable.

Order status transitions — only forward moves allowed; cancellation only from "Placed"

Implementation detail: The AllowedTransitions dictionary in OrderController defines valid transitions as a lookup table. Any attempt to skip a state or go backwards returns 400 Bad Request. Stock quantities are restored when an order is cancelled.
Security

Authentication & Authorization

Stateless JWT-based authentication with a three-tier role hierarchy. Every API request carries a self-contained token with the user's identity, role, and company membership.

JWT Token Structure

{
  "sub": "42",                      // User ID (NameIdentifier)
  "email": "priya@mcd.com",
  "name": "Priya Sharma",
  "role": "User",                   // User | CompanyAdmin | SuperAdmin
  "CompanyId": "3",                 // Tenant identifier (null for SuperAdmin)
  "iss": "CanteenApi",
  "aud": "CanteenApp",
  "exp": 1731686400                 // 8-hour expiry
}

Role Hierarchy

👑

SuperAdmin

CompanyId = null. Can see all companies' data, manage companies, access any analytics. Cannot place orders (no company context).

🔧

CompanyAdmin

Manages their company's menu items, daily stock, and orders. Sees the kitchen dashboard. Runs analytics queries. All scoped to their CompanyId.

👤

User (Employee)

Browse today's menu, place orders, view own order history, use AI chat. Can only see their company's menu and their own orders.

Auth Flow

1
Login Request

Client sends POST /api/auth/login with email + password. Server looks up user, verifies bcrypt hash.

2
Token Generation

Server creates JWT with claims (userId, email, name, role, companyId) signed with HMAC-SHA256. 8-hour expiry.

3
Client Storage

Client stores JWT and sends it as Authorization: Bearer <token> on every subsequent request.

4
Middleware Validation

ASP.NET JWT Bearer middleware validates signature, issuer, audience, expiry. Extracts claims into HttpContext.User.

5
Authorization Check

[Authorize(Roles = "CompanyAdmin,SuperAdmin")] attributes enforce role checks. Extension methods extract tenant context.

Interview tip: JWT trade-offs are a common follow-up. Pros: Stateless, self-contained, works across microservices. Cons: Can't revoke before expiry, token size grows with claims. Solutions: short expiry + refresh tokens, or a token blacklist in Redis.
Data Isolation

Multi-Tenant Architecture

The system supports multiple companies sharing a single database, with row-level security enforced through CompanyId filtering on every query.

How Tenant Isolation Works

// Every data query follows this pattern:
var companyId = User.GetCompanyId();  // From JWT claims
if (companyId is null && !User.IsSuperAdmin())
    return Forbid();

var query = db.MenuItems.Where(m => m.IsActive);

if (!User.IsSuperAdmin())
    query = query.Where(m => m.CompanyId == companyId);  // Tenant filter

// SuperAdmin sees everything; others see only their company's data
Key invariant: No controller ever returns data without checking CompanyId. The extension method User.GetCompanyId() extracts this from JWT claims, making it impossible to forget — it's always available from the authenticated context.
Intelligence Layer

AI Integration

Two AI-powered features demonstrate different patterns: an agentic chat assistant with tool use, and a Text-to-SQL analytics engine. Both use Claude Haiku via the official Anthropic C# SDK.

AI Chat — Agentic Loop with Tool Use

The chat assistant can look up the menu and place orders on behalf of the user through an agentic tool-calling loop.

Agentic loop: Claude decides which tools to call, the server executes them, results stream back via SSE

Agentic loop pattern: The ClaudeApiService runs up to 10 rounds. Each round: send conversation to Claude → if Claude returns tool_use, execute the tool locally → append result → send again. Loop terminates when Claude responds with text only (no more tool calls) or hits the round limit.

Analytics — Text-to-SQL

1
Admin asks a natural language question

"What were the top 5 most ordered items last week?" sent to POST /api/analytics/query.

2
System prompt provides the schema

Claude receives the full table definitions so it understands the data model. The prompt instructs it to output valid SQLite SQL.

3
Claude generates SQL

The model produces a SELECT query filtered by the admin's CompanyId for tenant isolation.

4
Server executes and returns results

SQL is run against the database. Results are formatted as a table with a natural language summary.

Security note: Text-to-SQL is powerful but risky. In production, add: SQL query validation (only SELECT), parameterized CompanyId injection, query timeout limits, result row limits, and possibly a query review step.
Request Lifecycle

Data Flow: Placing an Order

Walk through the most critical operation — placing a food order — from button click to database commit.

1
Client: Build the cart

User adds items from today's menu. Frontend tracks [{menuItemId, quantity}] locally. Only items from GET /api/stock/today are shown.

2
Client: Submit order

POST /api/order with {"items": [{"menuItemId": 4, "quantity": 2}]} plus Authorization: Bearer header.

3
Server: Extract tenant context

JWT middleware validates token. User.GetUserId() and User.GetCompanyId() extract authenticated identity. SuperAdmins rejected.

4
Server: Validate each line item

For each item: load today's DailyStock → verify item belongs to user's company → check QuantityAvailable - QuantityOrdered ≥ requested. Return 400 if any check fails.

5
Server: Create order atomically

Single SaveChangesAsync: create Order, create OrderItems with snapshotted prices, increment QuantityOrdered on each stock record, compute TotalAmount.

6
Server: Return 201 Created

Response includes the full order with items, status "Placed", and total. Kitchen dashboard picks up the new order on its next poll.

Concurrency handling: EF Core's change tracker groups all modifications into a single database transaction. If two users try to order the last serving simultaneously, one succeeds and the other gets a concurrency exception. In production, add optimistic concurrency tokens (RowVersion) on DailyStock.

Scalability Considerations

The current architecture is optimized for simplicity. Here's how each component evolves as the system grows from single-office to hundreds of companies.

Current State vs. Production Scale

Scaling Strategy: Step by Step

1

Migrate to PostgreSQL

Drop-in via EF Core — change connection string and provider. Gains: concurrent writes, connection pooling, JSONB, full-text search.

2

Add Caching Layer

Redis for frequently read data: today's menu (invalidate on stock changes), company settings. Cuts DB load by 60-70%.

3

Horizontal API Scaling

3+ API instances behind a load balancer. JWT is stateless, so no session affinity needed. Auto-scale on CPU/request count.

4

Async Processing

Move AI analytics to a background queue (RabbitMQ/Azure Service Bus). Admin gets "processing" status and is notified when results are ready.

5

Database Partitioning

Partition DailyStock by month and Order by quarter. Old data moves to cold storage. Current queries hit only today's partition.

6

CDN & Edge Caching

Static frontends from CDN. Menu images through CloudFront. API responses with short cache headers for public data.

Interview Discussion

Design Trade-offs

Every architectural decision is a trade-off. Discussing these in an interview shows deeper understanding than presenting a "perfect" design.

SQLite vs. PostgreSQL

Chose SQLite: Zero setup, no dependencies. Trade-off: No concurrent writes, no replication. Acceptable because the EF Core migration path to PostgreSQL is a config change.

Shared Schema Multi-Tenancy

Chose shared schema: Simplest to implement, cheapest to operate. Trade-off: One buggy query without CompanyId leaks data across tenants. Must be enforced at every query.

JWT Without Refresh Tokens

Chose simple JWT: Stateless, no extra storage. Trade-off: 8-hour window for compromised tokens, no immediate revocation. Production should add short-lived tokens + refresh rotation.

Polling vs. Push for Kitchen

Chose polling: Simple HTTP. Trade-off: Delay between order placement and kitchen visibility. WebSockets/SignalR would give instant updates.

SSE vs. WebSockets for Chat

Chose SSE: Simpler protocol, auto-reconnects, perfect for server-to-client streaming. Trade-off: Unidirectional — each turn needs a new HTTP POST.

Monolith vs. Microservices

Chose monolith: One deployment, shared transactions, simple debugging. Trade-off: Can't scale AI and ordering independently. At scale, split into Order/Menu/AI/Auth services.

Common Interview Follow-Up Questions

"How would you handle the lunch rush?" — Peak ordering in a 30-minute window. Solutions: pre-compute today's menu at stock-set time, cache aggressively, rate-limit per user, queue to smooth order processing, pre-authorize stock.

"How do you prevent overselling?" — Currently: EF Core transaction ensures atomic read-check-update. At scale: SELECT FOR UPDATE or optimistic concurrency tokens. Extreme scale: Redis pre-decrement counts, reconcile async.

"What if Claude is down?" — Circuit breaker pattern (fallback to "AI temporarily unavailable"), queue and retry, cache common responses, provide degraded experience with direct SQL for analytics.

"How would you add notifications?" — FCM for push. When order status changes to "Ready", push to user. Email: queue (don't block the API), process with background worker, use SendGrid.
