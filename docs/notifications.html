Order-ready notifications

How employees know their food is ready: a polling-based toast system that watches for status changes and alerts when an order moves to “Ready”.

Overview

When an employee places an order, it goes through a status pipeline: Placed → Preparing → Ready → Collected. The employee needs to know the moment their order hits “Ready” so they can pick it up from the counter.

This feature uses a REST-first polling strategy: a React hook polls the API every 10 seconds, compares each order's current status against its previously known status, and shows a toast notification when any order transitions to “Ready”. No WebSocket or SignalR connection is needed.

Why polling? pragmatic

Polling is simpler to build, debug, and deploy. For a canteen with dozens of concurrent users and order lifecycles measured in minutes, a 10-second poll interval is more than responsive enough. No infrastructure changes needed.

What gets built 4 files

  • GET /api/order/my/active — backend endpoint
  • getMyActiveOrders() — API client function
  • useOrderNotifications — polling hook
  • Toast.tsx — notification component

Future upgrade planned

SignalR can replace polling later. The hook's interface stays the same — only the data source changes from interval-based fetch to a hub connection that pushes events. See the SignalR section.

How it works

A complete notification cycle, from login to toast dismissal.

  1. Employee logs in

    App.tsx renders AppShell inside AuthProvider. AppShell calls useOrderNotifications(!!user). Since user is now truthy, the hook activates and begins polling immediately.

  2. Hook polls active orders

    The useEffect inside the hook calls getMyActiveOrders() immediately on mount, then sets up a setInterval that repeats the call every 10 seconds. The endpoint returns only orders with status Placed, Preparing, or Ready.

  3. Previous statuses are compared

    The hook keeps a useRef<Map<number, string>> that maps each order ID to its last-known status. On each poll, every returned order is compared against this map. The map is then updated with the current statuses.

  4. A “Ready” transition triggers a toast

    If an order had a previous status (meaning it was seen before) and that status was not “Ready”, but the current status is “Ready”, a new ToastMessage is added to the toasts state array. The toast text includes the order number and item names.

  5. Toast renders and auto-dismisses

    ToastContainer renders each toast as a ToastItem in the top-right corner with a slide-in animation. Each toast sets a setTimeout for 8 seconds, after which it calls onDismiss to remove itself. The user can also click the × button to dismiss it immediately.

  6. On logout, everything clears

    When user becomes null, the hook's useEffect cleanup runs: it clears the interval, empties the previous-statuses map, and clears any remaining toasts. No orphaned timers or stale state.

The first poll on login seeds the status map without triggering any toasts. This prevents a false notification for orders that were already “Ready” before the user opened the app.

Backend endpoint

[HttpGet("my/active")] MyActiveOrdersOrderController.cs

WhatReturns the current user's orders that are still in progress (not yet collected or cancelled).

Auth[Authorize] — any authenticated user. Returns only orders belonging to the caller (filtered by UserId from the JWT's NameIdentifier claim).

HowQueries orders where UserId matches the JWT claim and status is one of Placed, Preparing, or Ready. Includes the Items and their MenuItem navigation properties for the response DTO. Ordered by CreatedAt descending (newest first).

[HttpGet("my/active")]
public async Task<IActionResult> MyActiveOrders()
{
    var userId = int.Parse(
        User.FindFirst(ClaimTypes.NameIdentifier)!.Value);

    var orders = await db.Orders
        .Include(o => o.Items).ThenInclude(oi => oi.MenuItem)
        .Where(o => o.UserId == userId
                    && (o.Status == "Placed"
                        || o.Status == "Preparing"
                        || o.Status == "Ready"))
        .OrderByDescending(o => o.CreatedAt)
        .ToListAsync();

    return Ok(orders.Select(ToResponse));
}
MethodRouteAuthReturns
GET/api/order/my/activeAuthorizeArray of OrderResponse (id, status, totalAmount, createdAt, updatedAt, items[])

This endpoint is deliberately separate from GET /api/order/my (which returns all orders including collected and cancelled). Polling an endpoint that returns only active orders keeps the payload small and the query efficient — most users will have zero or one active order at any time.

Frontend components

Four pieces work together: the API function, the polling hook, the toast component, and the app shell that wires them up.

WhatFetches the current user's active orders from the backend.

HowA standard fetch call to /api/order/my/active with the JWT in the Authorization header. Returns a typed Promise<OrderResponse[]>.

export async function getMyActiveOrders(): Promise<OrderResponse[]> {
  const res = await fetch(`${API}/order/my/active`, {
    headers: authHeaders(),
  });
  if (!res.ok) throw new Error("Failed to load active orders");
  return res.json();
}

hooks/useOrderNotifications.ts polling hook

useOrderNotifications(loggedIn)hooks/useOrderNotifications.ts

WhatA custom React hook that polls for active orders and detects “Ready” transitions.

InputloggedIn: boolean — when false, the hook is inert (no polling, no toasts).

Returns{ toasts: ToastMessage[], dismiss: (id: string) => void }

HowUses three pieces of React state and refs:

  • toasts — useState<ToastMessage[]>, the active toast messages.
  • prevStatuses — useRef<Map<number, string>>, the last-known status of each order. Persists across renders without causing re-renders.
  • polling — useRef holding the interval timer ID for cleanup.
const POLL_INTERVAL = 10_000;

export default function useOrderNotifications(loggedIn: boolean) {
  const [toasts, setToasts] = useState<ToastMessage[]>([]);
  const prevStatuses = useRef<Map<number, string>>(new Map());
  const polling = useRef<ReturnType<typeof setInterval>>();

  const dismiss = useCallback((id: string) => {
    setToasts((prev) => prev.filter((t) => t.id !== id));
  }, []);

  useEffect(() => {
    if (!loggedIn) {
      prevStatuses.current.clear();
      setToasts([]);
      return;
    }

    async function check() {
      try {
        const orders = await getMyActiveOrders();
        const prev = prevStatuses.current;
        const next = new Map<number, string>();

        for (const order of orders) {
          const oldStatus = prev.get(order.id);
          next.set(order.id, order.status);

          if (oldStatus
              && oldStatus !== order.status
              && order.status === "Ready") {
            const itemNames = order.items
              .map((i) => i.name).join(", ");
            setToasts((t) => [...t, {
              id: `ready-${order.id}-${Date.now()}`,
              text: `Order #${order.id} is ready `
                  + `for pickup! (${itemNames})`,
            }]);
          }
        }
        prevStatuses.current = next;
      } catch {
        // silently ignore polling errors
      }
    }

    check();
    polling.current = setInterval(check, POLL_INTERVAL);
    return () => clearInterval(polling.current);
  }, [loggedIn]);

  return { toasts, dismiss };
}

components/Toast.tsx notification UI

ToastContainer + ToastItemcomponents/Toast.tsx

WhatA fixed-position container that renders toast notifications in the top-right corner.

HowToastContainer renders a ToastItem for each message. Each ToastItem:

  • Fades in with a slide-down animation on mount (opacity 0 → 1, translateY(-12px) → 0).
  • Sets a setTimeout for 8 seconds that calls onDismiss.
  • Shows an icon, the message text, and an × close button.
  • Uses a dark green background (#065f46) with white text and a rounded border radius.
export default function ToastContainer({
  messages, onDismiss,
}: {
  messages: ToastMessage[];
  onDismiss: (id: string) => void;
}) {
  return (
    <div style={styles.container}>
      {messages.map((msg) => (
        <ToastItem key={msg.id}
          message={msg} onDismiss={onDismiss} />
      ))}
    </div>
  );
}

// ToastItem highlights:
useEffect(() => {
  requestAnimationFrame(() => setVisible(true));
  const timer = setTimeout(
    () => onDismiss(message.id), 8000);
  return () => clearTimeout(timer);
}, [message.id, onDismiss]);

App.tsx wiring

AppShellApp.tsx

WhatA wrapper component that sits inside AuthProvider and activates the notification system globally.

HowReads user from useAuth(), passes !!user to useOrderNotifications, and renders ToastContainer above the router. This means toasts appear on every page — the employee sees the notification regardless of which page they're on.

function AppShell() {
  const { user } = useAuth();
  const { toasts, dismiss } =
    useOrderNotifications(!!user);

  return (
    <>
      <ToastContainer
        messages={toasts} onDismiss={dismiss} />
      <BrowserRouter>
        <Routes>
          {/* ... all routes ... */}
        </Routes>
      </BrowserRouter>
    </>
  );
}

export default function App() {
  return (
    <AuthProvider>
      <AppShell />
    </AuthProvider>
  );
}

Architecture

The data flow from app startup to a toast on screen.

Steps 3–7 repeat every 10 seconds. Step 7 only fires when a status actually transitions to “Ready”; otherwise the poll completes silently.

Configuration

Two constants control the notification timing. Both are defined as constants in their respective files.

SettingDefaultFileEffect
POLL_INTERVAL10,000 ms (10 s)hooks/useOrderNotifications.tsHow often the hook calls the API. Lower values mean faster detection but more network traffic. 10 seconds is a good balance for a canteen.
Auto-dismiss timeout8,000 ms (8 s)components/Toast.tsxHow long a toast stays visible before it fades out. The setTimeout is in the ToastItem component's useEffect.

To change either value, edit the constant in the respective file. No environment variable or config file is needed — these are compile-time constants baked into the frontend bundle.

Future: SignalR upgrade

The polling approach works well for a small canteen. For larger scale or lower latency, SignalR can replace the polling loop without changing the component architecture.

What stays the same

  • ToastContainer and ToastItem — unchanged.
  • AppShell wiring — still calls a hook that returns { toasts, dismiss }.
  • The GET /api/order/my/active endpoint — kept for initial load and fallback.

What changes

  • New backend: an OrderHub (SignalR hub) that broadcasts status changes. When OrderController.UpdateStatus saves a new status, it calls hub.Clients.User(userId).SendAsync("OrderStatusChanged", orderId, newStatus).
  • Hook rewrite: useOrderNotifications replaces setInterval + fetch with a HubConnectionBuilder that listens for "OrderStatusChanged" events. No polling needed.
  • Packages: @microsoft/signalr on the client, Microsoft.AspNetCore.SignalR on the server (included in the .NET framework).

SignalR adds complexity: connection lifecycle management, reconnection logic, authentication of the WebSocket handshake, and deployment considerations (sticky sessions or Azure SignalR Service). Only upgrade when polling becomes a bottleneck.
